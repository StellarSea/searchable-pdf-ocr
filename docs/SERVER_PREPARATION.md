# 서버 준비 단계의 분리 측정과 병렬 PDF 변환 후보

2026-09-14. 기존 `paddleocr-vl-api` 안에서 진단 프로세스만 실행했다.
서버 재시작, 모델 추가 로딩, 운영 설정/원본/캐시 변경은 없었다. HPS도 사용하지 않았다.
실행 전 사용자 OCR 프로세스가 없음을 확인했고, 완료 후 진단 작업자와 공유 메모리가
남지 않았으며 세 OCR 서비스가 healthy인 것을 확인했다.

## 실제 준비 단계의 비용

`tools/server_preparation_probe.py`는 서버의 `file_to_images`를 그대로 호출하고,
이전 HTTP 응답의 `layout_det_res`를 재사용한다. 모델 객체는 생성하지 않으며
`_PaddleOCRVLPipeline`의 CPU 함수만 호출한다. PDF는 원래와 같은 PDFium 렌더 경로다.

첫 10페이지 요청(11,839,113바이트, SHA는 DOCUMENT_REPEATABILITY.md와 동일)의 결과:

- 이미지 변환: **5.419초**, 이미지 합계 **1.61GiB**.
- 문서 내 그림 수집: 0.074초.
- 박스 준비 0→4→8→8→4→0 작업자: **0.370 / 0.161 / 0.110 / 0.120 / 0.121 / 0.152초**.
- JPEG 요청 생성 0→4→8→8→4→0: **0.326 / 0.341 / 0.304 / 0.307 / 0.300 / 0.316초**.
- 박스 준비의 ndarray 픽셀/전체 반환 메타데이터 해시가 전부 같았다.
  JPEG도 이미지 바이트·프롬프트·순서·생성 옵션을 포함한 요청 해시가 같았다.

워밍업/호스트 부하 영향을 고려하면 박스 준비와 JPEG 작업자 증가는 이 표본의 수초 단위
공백을 해결하는 핵심이 아니다. 따라서 이 옵션을 운영 서버에 무작정 켜지 않았다.
GPU layout 탐지 자체, HTTP 처리, 비동기 대기는 이 CPU 분리 측정에 포함되지 않는다.

`layout_prep_cpu_workers` 및 관련 CPU 함수가
[PaddleX v3.6.1 공식 소스](https://raw.githubusercontent.com/PaddlePaddle/PaddleX/v3.6.1/paddlex/inference/pipelines/paddleocr_vl/pipeline.py)에
있음을 확인했다. 이를 로컬 전용 옵션으로 판단할 이유는 없으며, 전체 설치 소스가 공식
소스와 바이트 단위로 일치하는지까지 검사한 것은 아니다.

## PDF 변환: 일반 프로세스 전달 vs 공유 메모리

`tools/server_pdf_parallel_probe.py`는 각 작업자에서 독립 PDFium 문서를 열고 같은
`render_pdf_page_to_numpy` 및 크기 제한 검사를 호출한다. `init_forms`도 유지한다.
PDFium/PyMuPDF 객체를 스레드 간 공유하지 않는다.

시간은 결과 이미지를 부모가 모두 받은 시점까지다. 픽셀 해시 비교는 시간 밖에서 수행한다.
모든 실행에서 10페이지의 크기·dtype·픽셀 SHA-256이 기존 순차 변환과 같았다.

| 전달 방식 | 작업자 | 첫 실행(초) | 같은 풀 재사용(초) |
|---|---:|---:|---:|
| 일반 배열 전달 | 2 | 7.973 / 6.790 | 5.348 / 5.149 |
| 일반 배열 전달 | 4 | 6.545 / 6.457 | 4.396 / 4.375 |
| 공유 메모리 | 4 | 5.632 / 5.332 | **3.036 / 2.841** |

일반 전달 비교의 순차 재실행은 4.728 / 4.669초, 공유 메모리 비교의 순차 재실행은
4.809 / 4.779초였다. 공유 메모리의 재사용 중앙값 **2.939초**는 같은 실험의 순차
재실행 중앙값 **4.794초**보다 약 **38.7% 짧다**. 전체 OCR의 속도 개선 수치가 아니다.
각 비교의 앞뒤 순차 실행과 모든 원시 시간은 아래 JSON에 보관했다.

공유 메모리는 부모가 생성/해제하고 작업자는 연결하여 채운 뒤 연결만 닫는다.
부모는 결과를 일반 소유 NumPy 배열로 복사한 뒤 공유 메모리를 해제한다. 이 최종 복사도
시간에 포함했다. 따라서 반환 이미지에 공유 메모리 뷰가 남지 않는다.

## 운영 적용 전 남은 조건 — 현재는 진단 후보

첫 작업은 병렬 방식이 오히려 느리므로 요청마다 풀을 새로 만들지 않는다. 이번 실험의
풀은 한 PDF의 bytes를 initializer로 전달하므로 **서로 다른 PDF를 연속 처리하는 운영
풀은 아직 구현한 것이 아니다**. 현재 OCR 명령의 운영 경로는 변경하지 않았다.

다음 구현은 다음 조건을 함께 충족해야 한다.

1. 서버 생명주기의 제한된 spawn 풀 재사용. GPU 모델/추론 객체를 자식에 넘기지 않는다.
2. 다른 PDF/다른 페이지 크기에서도 원본 요청과 같은 픽셀·순서·폼/회전 처리를 유지한다.
3. 최종 이미지, 공유 메모리, 작업자 임시 렌더 버퍼/프로세스 비용을 포함한 입장 예산.
   현재 메모리 여유만 믿고 모든 크기의 PDF를 무제한 공유 메모리에 올리지 않는다.
4. 부분 제출 실패·작업자 실패·시간 초과·취소 시 해당 풀을 회수한 후 공유 메모리 해제.
   운영 경로는 원래 순차 변환으로 복구할 수 있어야 한다.
5. 새 인식 입력 바이트/좌표 비교 및 전체 HTTP/OCR 시간을 실제 긴 문서에서 확인.
   문단 모델의 기존 반복 변동과 전처리 변경의 영향을 별도 기록한다.

진단 helper에는 정상 반환·작업자 실패·부분 제출 실패의 공유 메모리 회귀 3개를 추가했다.
반환 배열이 메모리를 직접 소유하고, 제출된 작업이 끝나기 전에 메모리를 해제하지 않으며,
종료 후 메모리에 재연결할 수 없는지 확인한다. 운영 timeout/메모리 안전장치를 구현한
것은 아니다. 현재 구조 검사: 70개 Python 파일 통과.
