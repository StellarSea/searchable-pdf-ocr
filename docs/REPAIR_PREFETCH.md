# 유실 보완 OCR의 CPU/GPU 겹쳐 실행

`repair_blocks`는 후보를 찾기 위해 모든 유효한 블록의 줄을 분석한다. 일부 후보만
GPU로 재인식한다. 이 단계에서 CPU 분석과 HTTP 응답 대기를 매번 직렬로 더하지 않도록 한다.
CHAPTER 등의 경계 확장(`ocr_boundary.repair`)과는 다른 단계이며 경계 보완은 아직 순차 처리다.

## 유지하는 계약

- 모델·API 옵션·렌더링 배율·PNG 픽셀·검출 임계값·문자/숫자 보존 판정은 바꾸지 않는다.
- 입력 페이지와 블록의 순서대로 같은 요청을 **한 번에 하나씩만** 보낸다. GPU 모델을 더 띄우지 않는다.
- PNG만 HTTP 작업자에 전달한다. 페이지, 줄 좌표 분석, 메타데이터, 판정과 SQLite/JSON 중간 저장은
  소유 스레드에 남긴다. PyMuPDF의 다중 스레드 접근은 없다.
- 이전 응답의 판정과 중간 저장이 성공해야 다음 요청을 전송한다. 다음 블록 준비가 실패해도
  앞서 전송한 요청은 먼저 회수한다. 중간 저장이 실패하면 다음 요청을 보내지 않는다.
- API 실패의 기존 동작을 유지한다. 체크포인트 콜백이 있으면 오류를 기록하고 중지하며,
  없으면 해당 블록을 유지하고 다음 블록을 진행한다. 완료된 `repair_audit`의 재개 규칙도 같다.
- CPU 준비는 단일 소유 스레드이고, HTTP 진행 중 PNG 하나 + 다음 PNG 하나로 제한한다.
  전체 문서의 이미지나 무제한 작업 목록을 미리 만들지 않는다. 기존 개별 crop 크기는 유지한다.

## 반복 렌더링 비용

한 페이지의 불변 그리기 명령(`PageRaster`)을 줄 탐지와 후보 PNG 렌더링에서 재사용한다.
전체 페이지 비트맵은 저장하지 않는다. 첫 유효 블록에 도달하기 전에는 만들지 않아,
중간 저장으로 완료된 페이지는 생성 자체를 건너뛴다. 그리기 명령 생성에 실패하면 기존
페이지 렌더링을 사용한다. 영속 탐지 캐시를 추가하거나 `ocr_render.py`의 구현 해시를 바꾸지 않는다.

## 적용과 복구

CLI의 유실 보완 및 `--repair-cache`에서 기본 적용된다. `--no-prefetch`로 보완 OCR과
기존 line-ocr의 CPU/HTTP 겹치기를 해제할 수 있다. 품질 검사나 인식은 생략하지 않는다.
라이브러리 `repair_blocks(..., prefetch=False)`는 호환성을 위해 순차 기본값을 유지한다.
진단 비교는 `reuse_raster=False`로 그리기 명령 재사용도 해제할 수 있다.
운영 캐시·기존 PDF·Docker 설정은 수정하지 않았으며 HPS를 재도입하지 않았다.

## 검증 및 재현

- 오프라인 회전 0/90/180/270도·cropbox·주석 표본: PNG 바이트, 줄 좌표, 결과, 판정,
  체크포인트를 재사용 없음/재사용/재사용+겹치기 간 비교한다.
- 이벤트 기반 검사로 실제 CPU 준비 중 HTTP가 진행되는지, 이전 체크포인트 이전에
  다음 요청이 시작하지 않는지, 준비/API/체크포인트 오류와 리소스 회수를 검사한다.
- `tools/benchmark_repair_render.py`는 완료된 기준 DB를 읽기 전용으로 열고 원본 해시를
  확인한 뒤 과거 보완 전 문자열을 복원하여 같은 블록을 검사한다. 각 판정의 순서와
  중간 저장 내용, 모든 줄 좌표, 전송 PNG SHA-256을 비교한다.
- 기본은 기록된 인식 응답을 사용하여 CPU 비용만 비교한다. `--overlap --live`는 같은
  현재 서버로 실제 인식하면서 순차/겹치기 방식을 교차 비교한다. 새 응답이 다르면
  비교를 성공으로 표시하지 않고 각 실행 결과를 남긴다. 모델의 반복 실행 변동 가능성은 별도다.

32페이지의 CPU 재사용만 교차 비교한 최초 결과(재사용 없음/있음/있음/없음):
57.32 / 53.20 / 52.38 / 53.17초. 각각 중앙값 55.25 / 52.79초.
405개 블록의 줄 좌표와 9개 보완 요청의 PNG·인식 문자열·판정·중간 저장은 모두 일치했다.
작은 시간 차이는 OS 캐시 등의 영향도
있으며 이 결과를 전체 OCR 속도나 GPU 공백 감소율로 해석하지 않는다.

원시 자료: `tmp/performance-max/repair-render-reuse/comparison.json`.

## 실제 서버 교차 비교 (2026-09-14)

같은 32페이지/405블록/9요청을 순차 → 개선 → 개선 → 순차 순서로 실행했다.
운영 작업이 없음을 확인한 뒤 기존 서버와 모델을 그대로 사용했다.

| 실행 | 재사용/겹치기 | 보완 단계 시간 | GPU ≤10% 표본 / 유효 GPU 표본 |
|---|---|---:|---:|
| 1 | 없음/없음 | 77.418초 | 65 / 76 |
| 2 | 있음/있음 | 59.392초 | 48 / 58 |
| 3 | 있음/있음 | 53.533초 | 47 / 53 |
| 4 | 없음/없음 | 76.350초 | 64 / 75 |

- 중앙값 76.884 → 56.463초, **보완 단계 약 26.6% 단축**. 전체 PDF 처리 시간은 아니다.
- 네 실행 모두 전송 PNG, 405블록의 줄 좌표, 실제 인식 문자열, 판정, 중간 저장 내용이 같았다.
  보완 채택 4개도 동일하다. 전체 책의 정답률이나 모든 모델 출력의 결정성을 증명하지는 않는다.
- GPU 표본은 약 1초 간격 `nvidia-smi`, age <2초만 포함했다. 순서대로 평균 8.34 / 8.81 /
  7.66 / 8.65%다. **GPU 평균 사용률 상승이나 낮은 구간의 완전 제거는 입증되지 않았다.**
  낮은 사용률 표본의 개수는 줄었지만 비율은 비슷하다. 이 단계는 GPU 요청 9개를 찾기 위해
  CPU에서 405블록을 분석하므로 여전히 CPU 중심이다. 다른 앱의 GPU 부하도 포함될 수 있다.
- 진단 프로세스 트리 RSS 최고는 실행별 약 1.32~1.62GiB, 호스트 가용 RAM 최저는
  약 11.0~12.3GiB였다. RSS 공유 메모리 중복과 외부 앱 부하가 포함될 수 있다.
- 모니터링을 포함한 네 실행과 검증 총 269.014초, 프로파일러 종료 코드 0.
- 최종 전체 오프라인 회귀 165개 통과(148.843초). 새 보완 관련 검사 11개를 포함한다.
  Python 61개 파일의 문법/미정의 전역과 구현 모듈 20개의 순환 의존성 검사도 통과했다.
  `git diff --check`는 공백 오류 없이 통과했다(LF/CRLF 변환 안내만 출력).

실제 비교 자료: `tmp/performance-max/repair-overlap-live/`,
자원 표본/명령 로그: `tmp/performance-max/repair-overlap-live-profile/`.

```powershell
python tools/profile_ocr_resources.py --out tmp/new-repair-profile -- python -u tools/benchmark_repair_render.py --source tmp/cpu_workers/production32/source.pdf --baseline tmp/performance-max/baseline-output --out tmp/new-repair-comparison --repeats 2 --overlap --live
```

요구하며 기존 기준 PDF/SQLite/캐시는 덮어쓰지 않는다.
