# 스캔 PDF OCR 사용 안내

처음 설치할 때는 [설치 안내](SETUP.md)를 먼저 읽는다. 명령은 저장소 루트 기준이며,
아래 과거 `C:\ocr` 예시는 자신의 체크아웃 경로로 바꾼다. 실측 수치는 당시 환경의 기록이다.

프로젝트 폴더에서 `python run.py PDF경로` 또는 `python run.py 폴더경로`로 실행한다.
품질 검사는 `python run.py audit 결과경로`, 회귀 테스트는 `python run.py test`다.
아래의 `compose` 내부 스크립트 직접 실행도 계속 지원한다.

600 DPI TIFF 스캔을 ScanTailor Advanced로 보정하는 경우에는
[ScanTailor Advanced → TIFF → PDF → OCR 작업 안내](SCANTAILOR_WORKFLOW.md)부터 시작한다.
Tools → Fix DPI에서 입력 해상도 확인, Output에서 600 DPI 설정과 TIFF 태그 자동 적용,
보정 TIFF 합치기, PDF 물리 크기 검사와 굿노트 확인을 포함한다.

### 출력 파일 정리

출력 폴더 최상위에는 `이름_auto_searchable.pdf`를 둔다. `.ocr/`의 책별 내부 자료는
`이름_line_ocr.sqlite3` 하나에 통합하며, 중복 실행 방지용 `이름.lock`은 유지한다.
디버그 PDF는 `--debug-lines` 사용 시, 미완성 PDF는 작업 중/게시 실패 시에만 필요하다.
본문 Markdown·JSON 보고서·상태·경계 페이지 체크포인트·격리 캐시는 SQLite의 `artifacts`
테이블에 원래 이름과 내용으로 보관한다. 아래 설명의 보조 파일명은 이제 DB 안의 항목명이다.
배치 전체 로그와 요약은 별도로 `.ocr/batch_logs/`, `.ocr/batch_status.json`에 유지한다.

`python run.py compact 기존출력폴더`는 인식 없이 기존 JSON/MD를 DB에 통합하고,
DB 무결성·바이트 검증 후 중복된 기존 파일을 삭제한다. 작업 중이거나 내용 충돌이 있으면 중단한다.
개별 PDF 재실행도 잠금을 획득한 뒤 해당 문서 자료를 자동 통합한다. 원본/완성 PDF는 건드리지 않는다.
`python run.py export "책_line_ocr.sqlite3" "내보낼폴더"`로 원래 JSON/MD를 필요할 때 복원한다.
다른 내용의 기존 파일을 덮어쓰지 않는다. DB만 남아 있어도 재개·배치 완료 확인·품질 검사가 가능하다.
`organize`는 이전 방식의 폴더 이동 기능으로 남긴다. 개발용 도구가 물리 JSON 경로만 받는다면
먼저 `export`를 사용한다. 일반 실행과 품질 검사는 이전 파일 참조 및 `DB경로::항목명`을 읽는다.

완료 상태는 결과를 생성한 원본과 실행 옵션에 연결된다. 이전 상태에 원본 정보가 없으면
최초 한 번은 캐시를 재사용하여 결과를 다시 만든다. 빠른 모드·선택 페이지 모드·문단 모드도
별도 상태를 기록한다. `--no-cache`와 `--repair-cache`는 배치 완료 건너뛰기를 해제한다.
재귀 배치는 출력 폴더와 생성 PDF를 제외한다. `--out`은 PDF·상태·배치 로그에 모두 적용된다.
품질 판단은 성공한 보고서에 보존하고 실패한 검증 보고서는 `_failed_report`에 별도로 쓴다.

최종 검증의 CPU 병렬화는 일반 PDF에서 기본 최대 8개 작업자를 사용한다. `--verify-workers 0`은
검증만 순차로 돌린다. 기존 `--cpu-workers`와 `--cpu-memory-mb` 제한도 적용된다.

Docker API의 PDF 이미지 변환은 별도의 CPU 작업자 4개를 재사용한다. 모델/해상도는 그대로이며,
메모리 부족·작업자 실패는 기존 변환으로 복구한다. 이미지 보완 단계에서는 이 풀을 회수한다.
설정과 해제 방법은 `SERVER_PDF_POOL.md`를 참고한다. 기존 OCR 명령은 그대로 사용한다.
메모리/작업자 오류가 나면 검사를 생략하지 않고 모든 페이지를 순차 재검사한다.
작은 문서와 `--debug-lines`의 문자 검증은 순차 처리한다. [상세/실측](PARALLEL_VERIFICATION.md) 참고.

## 기본 사용법: PDF 경로만 입력

책갈피 목차를 자동으로 넣으려면 `--bookmarks`를 추가한다.
예: `python run.py "input/book.pdf" --out output --bookmarks`.
인쇄된 목차를 본문 제목과 대조하여 확인된 항목만 등록하고, 모호한 항목은 보고서에 남긴다.
기존 책갈피가 있는 PDF는 그대로 보존한다. 이 기능은 기본으로 켜지지 않는다.
지원 형식과 정확도 제한은 [자동 책갈피 안내](BOOKMARKS.md)를 참고한다.

이미 변환된 결과는 `python run.py bookmarks "input/ocr_output"`으로 책갈피만 갱신할 수 있다.
OCR을 다시 호출하지 않으며 기존 완성본을 백업하고 전 페이지 픽셀·글자·좌표를 대조한 뒤 교체한다.
기존 생성 책갈피를 사용자가 수정한 경우에는 덮어쓰지 않고 중단한다.

```powershell
python run.py "input/book.pdf"
```

현재 기본값은 **정밀 자동 모드**다. 결과는 원본 폴더 아래 `ocr_output`에 생성된다.
위 예시는 `input/ocr_output/book_auto_searchable.pdf`가 최종 결과다.
출력 위치만 바꾸려면 `--out output`을 추가한다.

본문 OCR은 다음 묶음을 미리 준비해 HTTP 요청을 최대 2개까지 겹친다. `--ocr-requests 1`을
추가하면 기존 순차 요청으로 돌아간다. 페이지 순서와 인식 설정은 유지하며 다음 실행부터 적용된다.
`--batch 0`에는 적용하지 않는다. [본문 요청 겹치기/제한](DOCUMENT_PREFETCH.md) 참고.

자동 모드의 CPU 페이지 준비는 최대 16개 작업자가 기본이다(논리 CPU 수 이하). 캐시가 있으면 준비를 생략하고,
메모리 부족/작업자 실패 시 기존 순차 처리로 복구한다. `--cpu-workers 0`으로 직접 해제하거나
`--cpu-memory-mb 16384`으로 추가 준비 메모리 예산(MiB, 기본 16 GiB)을 지정할 수 있다.
CPU/HTTP 대기 중에도 완료된 작업을 회수하고 다음 페이지를 보충한다. 결과는 원래 페이지
순서로 사용하며, 준비 창은 최대 32페이지와 메모리 예산으로 제한한다. 변경은 다음 실행부터 적용된다.
GPU 모델/해상도/캐시 키는 유지된다. 자세한 제한과 검증은 [CPU 준비 안내](CPU_PREPARATION.md)를 참고한다.
준비된 줄 PNG는 기본적으로 언어별 최대 64개씩 묶어 GPU에 선행 전송한다. 큐는 최대 2개이며
실패하면 문단별 처리로 복구한다. `--no-gpu-prefetch`로 해제한다. [GPU 공급/실측](GPU_PREFETCH.md) 참고.

- 10페이지씩 OCR하고 누락 의심 블록을 보완 인식한다.
- 전 페이지의 여러 줄 본문을 줄별로 재인식하여 경계를 정렬한다. 한글과 영문에 적용한다.
- 줄 재인식 모델은 블록 단위로 고른다. 한글이 한자·가나보다 많으면 한글 전용 모델을,
  아니면 기본 모델을 쓴다. 기본 모델의 사전에는 한글이, 한글 모델의 사전에는 한자와
  가나가 없어서 한 모델로 둘 다 읽을 수 없다. 아래 "어떤 글자를 읽을 수 있나" 참고.
- 문구를 임의로 바꾸지 않는다. 인식 결과가 크게 다르면 기존 문구를 유지하고 보고서에 표시한다.
  작은 차이는 표시하지 않는다. 줄 인식 모델은 글자 단위로 정확하지 않으므로 거의 모든
  페이지가 표시되어 보고서가 쓸모없어지기 때문이다. 숫자와 주소가 바뀐 경우는 차이가
  작아도 항상 표시한다.
- 줄 경계는 라틴 단어나 숫자 안쪽에 놓지 않는다. 인식 결과가 한두 글자 어긋나도 가까운
  단어 경계로 되돌린다. 한글은 인쇄물에서 음절 사이로 줄이 넘어가므로 그대로 둔다.
- HTML 표와 복잡한 수식은 기존 배치 방식으로 처리하고 정밀 줄 검증 제외 대상으로 표시한다.
  이 표시는 페이지 단위다. 한 페이지에 블록이 40개라도 그중 하나만 수식이면 페이지 전체에
  `complex_structure`가 붙는다. 페이지 전부가 제외됐다는 뜻이 아니다. 실제로 어느 물리
  교재는 페이지의 84%에 이 표시가 붙었지만 블록 기준으로는 3,875개 중 2,750개(71%)가
  평문이어서 줄 정렬을 그대로 받았다.
- 이미 텍스트가 있는 페이지는 중복 삽입하지 않고 보존한다. 부분적으로만 텍스트가 있는 페이지도 이 방식으로 보존되므로 보고서 확인이 필요하다.
- 모든 페이지의 문자 추출, 투명 텍스트 여부, 72dpi 원본 화면 일치를 검사한다.
- 최종 검증에 실패하면 기존 완성 PDF를 덮어쓰지 않는다. 후보 파일은 `.partial.pdf`로 남는다.

`book_auto_report.md`는 확인할 페이지 목록, `book_auto_report.json`은 상세 검사 결과,
`book_auto_status.json`은 작업 상태다. `completed_with_warnings`는 처리는 끝났지만
원본 대조가 필요한 페이지가 있다는 뜻이다. 경고가 없어도 OCR 정확도를 보장하지 않는다.

### 중단 후 재개

같은 명령을 다시 실행한다. 완료된 OCR 배치와 줄 이미지는 재사용한다.
자동 모드의 줄 캐시는 `book_line_ocr.sqlite3`에 한 줄씩 저장하며,
보완 인식도 중간 저장한다. PDF 렌더링과 최종 검증은 다시 수행한다.
같은 출력에 대한 동시 실행은 잠금으로 차단한다.

속도 최적화는 해상도·인식 모델·줄 여백을 낮추지 않는다. 페이지의 그리기 명령을
한 번 읽어 줄 탐지와 OCR crop 생성에서 공유하며, 거대한 전체 페이지 비트맵을
미리 만들지는 않는다. 원본 SHA-256·페이지·회전/cropbox·crop 좌표·렌더러 버전과
설정·모델이 일치하는 줄은 PNG 생성 전에 캐시를 조회한다.
기존 줄 캐시는 보존한다. 옛 캐시에는 좌표 색인이 없으므로 처음 한 번은 렌더링하여
이미지 캐시와 연결하고, 그다음부터 일치하는 줄의 렌더링과 PNG 압축도 생략한다.
보고서의 `line_cache_stats`에서 `rendered_crops`와 `early_cache_hits`를 확인할 수 있다.
이 수치는 줄 인식용 crop만 집계하며 줄 탐지·최종 검증 렌더링은 포함하지 않는다.
이미 실행 중인 프로세스에는 적용되지 않고 다음 실행부터 사용된다.

원본 또는 API 설정이 다른 기존 캐시는 자동으로 신뢰하지 않는다.
자동 모드에서는 기존 캐시를 보존하고 `.ocr_cache` 아래에 별도 검증된 캐시를 만든다.
`--no-cache`는 문단 OCR을 다시 요청하지만 일치하는 중간 저장 및 줄 이미지 캐시는
재사용할 수 있다. 서버 모델을 바꾼 경우에는 기존 줄 캐시를 분리해서 보관해야 한다.

줄 캐시의 키에는 사용한 모델이 들어간다. 따라서 기본 모델로 받아둔 한글 줄 캐시는
한글 모델로 바꾼 뒤 조회되지 않고, 해당 줄만 다시 인식한다. 영문 줄 캐시는 그대로
재사용한다. 조회되지 않는 옛 항목도 SQLite에 보존한다. 이 DB에는 보고서·상태·원문도 함께
저장되므로 캐시 용량을 줄이려고 삭제하지 않는다. 별도 보관이나 이관 전에는 백업한다.

### 사전 준비와 시간

RTX 5080에서 실제 줄 표본을 비교한 결과, 현재 작은 블록별 요청에는 GPU 작업자
1개가 4·6·8개보다 유리하여 기본값을 1로 조정했다. 모델과 해상도는 유지하며,
기존 줄 캐시도 재사용한다. `LINE_OCR_WORKERS` 환경 변수로 조정할 수 있고
`/health`의 `workers`로 실제 적용값을 확인한다. 세부 조건과 한계는
`docs/GPU_WORKER_BENCHMARK.md`에 기록했다. 아래 과거 시간 측정치는 이번 튜닝의
전체 문서 재측정 결과가 아니다.

Python과 아래 패키지, Docker Desktop, 현재 Compose 설정 및 OCR 이미지가 미리 설치되어 있어야 한다.
서버가 꺼져 있으면 자동 시작을 시도하며 준비 상태를 최대 약 5분 기다린다.
이미지를 자동 다운로드하거나 새 모델을 설치하지는 않는다.
일시적인 API 오류는 최대 3회 시도하고, 계속 실패하면 재개 가능한 상태로 중단한다.
RTX 5080에서 170페이지 스캔본을 측정한 단계별 비용은 다음과 같다. 문단 OCR 약 2.4초/페이지,
줄 검출과 crop 생성 약 0.39초/페이지, 줄 인식 약 265줄/초, PDF 합성과 최종 검증 약 0.2초/페이지다.
최초 실행은 170페이지가 약 9분, 300페이지가 약 15분이다. 문단 캐시만 있고 줄 캐시가 없으면
170페이지가 약 220초, 줄 캐시까지 있으면 약 100초에 다시 만든다.
전체 시간의 약 8할이 문단 OCR이므로 줄 인식 쪽을 빠르게 해도 전체 시간은 거의 줄지 않는다.
페이지 밀도에 따라 달라지므로 다른 문서에서는 다시 측정해야 한다.

### 빠른 모드와 선택 페이지 모드

`--fast`는 기존 폭 기반 처리로 실행하며 전 페이지 줄 인식과 자동 최종 검증을 생략한다.
`--line-ocr-pages 13,17,26`은 기존 선택 페이지 모드이며 자동 모드와 다른 경로다.
아래의 선택 페이지 모드 설명과 기존 캐시 사용법은 이 모드들에 관한 것이다.

## 설치 환경

현재 검증한 구성은 Windows에서 저장소의 `compose/` 설정을 사용한다. 문단 OCR 서버는 8080,
줄 재인식 서버는 8081 포트다. Python에는 `requests`, `pymupdf`, `pypdf`, `numpy`가
필요하며, 별도의 검증 스크립트를 실행할 때는 `Pillow`도 필요하다.

서버를 직접 호출할 때는 `localhost`가 아니라 `127.0.0.1`을 쓴다. 이 PC에서
`localhost`는 IPv6를 먼저 시도하다 실패하여 연결마다 약 21초를 더 쓴다. 한 번 맺은
연결을 재사용하면(`requests.Session`) 이 비용이 없다.

긴 줄은 한 번에 인식하지 않고 조각으로 나눈다. 자를 위치는 잉크가 없는 빈 칸 중에서만
고른다. 글자를 관통해서 자르면 그 글자가 인식 결과에서 사라지고 줄 경계가 밀리기 때문이다.
빈 칸이 없으면 자르지 않고 넓은 조각을 그대로 보낸다. 모델이 가로로 눌러서 읽을 뿐
글자를 잃지는 않는다. 넓은 틈은 낱말 사이로 보아 공백으로 이어 붙이고, 좁은 틈은 글자
사이로 보아 붙여 쓴다.

`LINE_OCR_INPUT_WIDTH`는 320을 유지한다. 모델이 이 폭 기준으로 학습되어 있어 폭을 키우면
짧은 줄에 빈 여백이 과하게 붙고 정확도가 떨어진다. 768로 올려 측정했을 때 영문 블록
정렬 성공률이 93%에서 86%로 내려갔다. 긴 줄은 폭을 키우는 대신 위와 같이 나눠서 처리한다.

줄 재인식 모델은 `C:\ocr\models\official_models` 아래 두 개를 마운트한다.
`PP-OCRv5_mobile_rec`(기본, 영문·중국어·일본어)와 `korean_PP-OCRv5_mobile_rec`(한글).
한글 모델의 사전에는 라틴 문자와 숫자도 있어 한글·영문 혼용 줄을 처리할 수 있다.
`curl http://127.0.0.1:8081/health`의 `models` 항목으로 두 모델이 올라왔는지 확인한다.

출력 위치와 한 번에 전송할 페이지 수를 직접 지정하는 예시는 다음과 같다.

```powershell
python C:\ocr\compose\ocr_to_searchable_pdf.py "C:\ocr\input\book.pdf" --out "C:\ocr\output" --batch 10
```

문단 OCR 요청의 응답 대기 시간은 요청당 최대 600초다. 반환된 페이지 수가 요청한 수와
다르면 처리를 중단해 이후 페이지가 잘못 연결되는 것을 막는다. 완료된 배치는
`<이름>_partial.json`에 저장한다. 원본, API 설정, 배치 크기가 같으면 재실행할 때 이어서 처리한다.

## 캐시와 보완 인식 옵션

새 캐시에는 원본 파일의 식별값과 API 설정을 기록한다. 자동 모드는 일치하지 않는 기존
캐시를 보존하고 별도 캐시를 사용한다. 빠른 모드와 선택 페이지 모드는 불일치한 캐시를 거부한다.
원본 식별 정보가 없는 오래된 캐시를 이 모드에서 사용하려면 원본이 맞는지 확인한 뒤
`--trust-cache`를 추가한다. 확인되지 않은 캐시를 억지로 재사용하면 다른 문서의 텍스트가 들어갈 수 있다.

빠른 모드는 캐시가 있으면 문단 OCR을 재사용한다. 경계 잘림이 발견되면 확대 영역을
재인식할 수 있다. 자동 모드는 줄 이미지 캐시가 부족하면 API를
추가 호출한다. `--repair-cache`는 저장된 문단의 누락 의심 영역을 다시 확인하는 옵션이고,
`--no-repair`는 문단 보완 인식을 생략하는 옵션이다. `--no-repair`만으로 줄별 인식까지 꺼지지는 않는다.

보완 인식의 원문, 후보 문구, 반영 여부는 `repair_audit`에 기록한다. 기존 단어·주소·숫자가
유지되는지 검사하지만, 이 조건을 통과했다고 인식 내용이 반드시 정확한 것은 아니다.

## 줄 위치 확인

기본 실행은 **블록 경계의 글자 잘림도 자동 검사**한다. 상하좌우 경계를 가로지르는
잉크가 있으면 공백까지 영역을 넓히고, 레이아웃 검출을 끈 상태에서 확대 영역을
다시 읽는다. 옆 블록과 구분선은 확대 대상에서 제외한다. 기존 문자가 순서대로
모두 남아 있고 기존 숫자가 유지되는 결과만 채택한다. 거부된 결과는 원래 문구와
확대 좌표를 사용하고 보고서에 원본 확인 경고를 남긴다.

이 검사는 문단 OCR 캐시를 재사용하는 실행에도 적용된다. 검사·재인식 결과는
`.ocr/이름_boundary_cache.json`에 원본 지문과 알고리즘 버전별로 저장되며, 원시 OCR
캐시는 수정하지 않는다. 최초 실행에는 페이지 분석 및 잘린 블록 재인식 시간이
추가된다. 다음 실행은 검증 캐시를 재사용한다. `--no-boundary-repair`로 끌 수 있다.
경계에서 완전히 떨어진 누락 단어나 저대비·복잡한 그림까지 모두 복원하는 기능은 아니다.

원본 대조로 확인한 글자 누락과 잘린 좌표는 `--layout-review 교정.json`으로 함께
교정할 수 있다. 이 파일은 원본 PDF의 SHA-256과 교정 전 OCR 블록이 모두 일치할
때만 적용된다. `pages`의 각 항목에는 `page`, `reason`, `original_blocks`, `lines`를
기록하며, 각 줄은 `text`와 OCR 이미지 좌표의 `bbox`를 가진다. 검토한 줄·셀은
다시 분할하지 않고 직접 배치한다. 원시 OCR 캐시는 유지된다. 실행 시 이 옵션을
지정해야 적용되며, 교정 파일 변경도 완료 상태의 재사용 판단에 반영된다.

문서별 교정은 원본을 직접 대조해 작성한다. 이전 실험의 `tools/build_toc_review.py`와
`reviews/` 자료는 특정 책의 전사 내용을 포함하는 로컬 자료로 공개 저장소에 포함하지 않는다.
교정 파일 형식은 위 설명과 `tests/test_ocr_regressions.py`의 작은 합성 예제를 참고한다.

`--debug-lines`를 추가하면 텍스트 배치 영역에 빨간 테두리를 그린다. 자동 모드에서는
`<이름>_auto_debug.pdf`가 생성된다. 이 파일은 확인용이며 테두리가 없는 최종본과 다르다.
테두리가 있으므로 이 모드에서는 원본 화면과의 픽셀 일치 검사를 생략한다.

일반 결과 PDF는 투명 텍스트만 추가하며, 원본 페이지의 회전과 잘림 설정을 유지한다.
테두리는 페이지 분석이 끝난 뒤 그려 다음 영역의 줄 검출에 섞이지 않도록 한다.

표의 열 경계가 충분히 확인되는 경우에는 셀별 배치를 사용한다. 지원하지 않는 표 구조는
일반 텍스트 분배 방식으로 처리한다. 이메일 주소, 부등호, 서로 다른 위치에 반복되는 문구는 보존한다.
기본 글꼴에 없는 문자는 설치된 Windows 보조 글꼴을 사용한다.

화면에 `insertion failed`가 나오면 텍스트 삽입 실패를 뜻한다.
`boxes without assigned text`는 검출된 상자 중 텍스트가 배정되지 않은 상자가 있다는 뜻이다.
이 상자는 잡음일 수도 있고 실제 글자가 빠진 영역일 수도 있다.
삽입 실패가 0개여도 원문 전체가 정확하게 인식됐거나 줄 위치가 모두 맞는다는 뜻은 아니다.

## 한글과 수식 처리의 한계

폭 기반 배치는 한글 음절 사이에서 줄을 나눌 수 있지만 영문 단어와 숫자는 유지한다.
실제 줄 이미지를 사용하지 않는 경우에는 원본과 대체 글꼴의 폭 차이로 한두 음절이 밀릴 수 있다.

인라인 수식은 사람이 실제로 검색창에 입력할 문자로 바꾼다. 그리스 문자와 연산자
(`\Delta`→Δ, `\theta`→θ, `\times`→×, `\approx`→≈ 등 80여 개), 숫자 첨자(`x_{0}`→x₀,
`v^{2}`→v²), 함수 이름(`\sin`→sin)을 바꾸고 `\mathrm` `\mathbf` `\text` 같은 장식은 벗긴다.

`\Delta V`는 `ΔV`로 붙인다. TeX에서 명령 뒤 공백은 명령을 끝내는 기호일 뿐이고 사람도
검색할 때 붙여 쓰기 때문이다. 반면 `a \leq b`는 이항 연산자라 `a ≤ b`로 공백을 남긴다.

변환은 수식 하나 단위로 전부 아니면 전무다. 바꾼 결과에 역슬래시·중괄호·첨자 기호가
하나라도 남으면 그 수식은 손대지 않는다. 분수, 행렬, `\overline` 같은 장식, 알 수 없는
명령이 여기 해당한다. 달러 기호 사이에 역슬래시도 첨자 기호도 없으면 수식이 아니라
통화로 보고 건드리지 않는다. `$100$`은 그대로 남는다.

`𝓍`(U+1D4CD) 같은 수학 알파벳 기호는 쓰지 않는다. 검색창에 그 글자를 넣는 사람이 없고,
쓰면 평범한 `x`로 검색했을 때 오히려 걸리지 않게 된다.
원시 OCR 캐시와 Markdown은 보존한다. PDF 문자 검사는 검색용으로 변환한 텍스트를 기준으로 하며,
변환 전 수식 명령 문자열과 문자 하나하나가 동일한지 검사하는 것은 아니다.

## 고급: 특정 페이지만 줄별 재인식

보통은 기본 자동 모드를 사용하면 된다. 이전 방식으로 특정 페이지만 처리하려면 다음과 같이 실행한다.

```powershell
python C:\ocr\compose\ocr_to_searchable_pdf.py "C:\ocr\input\book.pdf" --line-ocr-pages 13,17,26
```

번호는 책에 인쇄된 쪽수가 아니라 **PDF의 첫 페이지를 1로 세는 순서**다.
`all`을 지정하면 전 페이지를 대상으로 한다. 이 선택 페이지 모드는 HTML이 아닌 여러 줄
한글 문단을 대상으로 하며, 기본 자동 모드와 처리 범위가 다르다.
결과는 `<이름>_line_searchable.pdf`, 테두리 확인용은 `<이름>_line_debug.pdf`다.

이 모드의 줄별 응답은 `<이름>_line_ocr.json`에 저장한다. 자동 모드의 SQLite 캐시와는
저장 방식이 다르다. 실제 이미지와 API 설정이 일치하는 결과를 재사용한다.
재인식 결과는 줄 경계에만 사용하고 원래 문단 문구는 유지한다.
차이가 큰 후보는 반영하지 않는다. API 오류가 발생하면 남은 미저장 이미지의 요청을 멈추고
기존 배치로 처리한다. 따라서 서버 장애 시 중단하는 기본 자동 모드와도 동작이 다르다.

## 고급: 원본 대조 후 문구 교정

자동 또는 선택 페이지 모드에서 `--line-ocr-review 교정파일경로`를 추가하면 직접 검토한 교정을 적용할 수 있다.
일반 자동 실행에는 교정 파일이 필요하지 않다.

교정 파일은 JSON 형식이며, 줄별 판단 기록의 `block_key`를 기준으로 다음 항목을 지정한다.

- `original`: 교정 전 문단 전체
- `replacement`: 교정 후 문단 전체
- `reason`: 원본 대조 근거

교정은 원래 문단과 줄 이미지의 식별값이 맞는 경우에만 적용한다. 일치하지 않으면 경고한다.
원시 인식 결과와 적용한 문구는 기록에 남는다. 교정 파일은 반드시 실제 원본을 확인해서 작성해야 하며,
다른 책의 교정 파일이나 모델이 추측한 정답을 그대로 재사용하면 안 된다.
줄 OCR의 경계 판정이 거절돼도 식별값이 일치하는 명시적 교정문은 적용한다. 이 경우
원래 줄 배치를 경계 안내로 사용하고 교정문의 문자를 모두 보존한다. 감사 기록의
`accepted`는 계속 모델 경계의 판정이며, 적용 문구는 `reviewed`와 `selected`에서 확인한다.

## 사람 손 없이 품질 확인하기

결과 PDF의 품질을 사람이 원본과 대조하지 않고 확인하는 방법이다.

```powershell
python C:\ocr\compose\audit_ocr_quality.py "C:\ocr\input\ocr_output\book_auto_searchable.pdf"
```

번호가 매겨진 문제집이면 `--items 1-100 --copies 10`을 덧붙인다. 일반 책에는 붙이지 않는다.

**검출 누락 점검**은 페이지의 잉크에서 검출된 블록을 뺀 나머지를 본다. 레이아웃 모델이
아예 보지 못한 영역은 이후 단계가 전부 "찾은 블록"에서 출발하므로 어디서도 드러나지 않는다.
파이프라인의 문자 수 검사도 PDF와 OCR 텍스트를 비교할 뿐 페이지와 비교하지 않는다.
그래서 이 검사만 페이지 픽셀을 직접 본다. 실제로 이 검사가 `기출 TEST 10` 표지에서
큰 숫자 `10`이 통째로 검출되지 않은 것을 찾아냈다.

잉크는 어둡기가 아니라 국소 대비로 센다. 남색 배경에 인쇄된 페이지를 통째로 잉크로 세면
모든 컬러 페이지가 누락으로 잡히기 때문이다. 사진은 걸리지 않는다. 검출된 이미지 블록
안에 있으므로 덮인 것으로 센다. 책등 쪽 검은 여백은 가장자리 2%를 빼서 무시한다.

**문항 번호 점검**은 책이 반드시 담고 있어야 하는 번호가 추출 텍스트에
실제로 있는지 센다. 없으면 그 자리에서 결함이다. 글자를 잃었거나 엉뚱한 곳에 붙었다는 뜻이다.
`--items`는 한 회분의 번호 범위, `--copies`는 그 범위가 책에 몇 번 반복되는지다.
번호를 런으로 끊지 않고 출현 횟수로 세므로, 문제의 보기 그림으로 들어간 양식이 자기 항목을
1부터 번호 매겨도 오탐이 생기지 않는다.

**두 모델 일치율**은 같은 픽셀을 서로 다른 두 모델이 읽은 결과를 글자 단위로 비교한다.
문단은 문서 VLM이, 줄은 작은 줄 인식기가 읽었고 그 판단이 줄 캐시에 남아 있다.
일치율이 낮은 페이지 목록이 먼저 볼 곳이다.

일치율이 높다고 둘 다 맞다는 뜻은 아니다. 스캔 품질이 나쁜 같은 자리에서 두 모델이 똑같이
틀릴 수 있다. 이 값은 정확도가 아니라 "여기를 보라"는 표시로 읽어야 한다.
진짜 글자 정확도는 사람이 원본을 보고 옮겨 적은 기준이 있어야 구한다.

합성 PDF로 정답을 만들어 재는 방법은 쓰지 않는다. 깨끗하게 렌더한 글자는 실제 스캔보다
훨씬 읽기 쉬워서 정확도가 과대평가되고, 파이프라인 자체의 회귀는 이미 테스트가 잡는다.

### 어떤 글자를 읽을 수 있나

줄 인식 모델이 만들어낼 수 있는 문자는 사전에 든 것뿐이다. 사전에 없는 문자는
인식 결과에서 빠지고, 줄 정렬이 거부되어 폭 기반 배치로 돌아간다. 문단 OCR을 맡는
VLM은 이 제한을 받지 않으므로 본문 문구 자체는 유지된다.

| | 기본 모델 | 한글 모델 |
|---|---|---|
| 영문·숫자·그리스 문자·수학 기호 | 있음 | 있음 |
| 서유럽 악센트(é ü ñ ß) | 있음 | 있음 |
| 한글 | **없음** | 있음 |
| 한자·가나 | 있음 | **없음** |
| 중동부 유럽 확장(ą ř ğ) | 일부 | 없음 |
| 키릴 문자 | **거의 없음** | 없음 |

블록마다 한글과 한자·가나 중 많은 쪽을 보고 모델을 고른다. 러시아어처럼 키릴 문자가
주인 책을 스캔하려면 모델을 하나 더 설치해야 한다. `eslav_PP-OCRv5_mobile_rec`를
`C:\ocr\models\official_models`에 받고, `compose.yaml`에 마운트를 추가한 뒤
`line_ocr_server.py`의 `MODELS`에 항목을 넣고 `line_language`가 그 문자를 고르게 하면 된다.
`LINE_ENGINE` 문자열도 함께 바꿔야 기존 캐시와 섞이지 않는다.

## 여러 권을 한 번에 처리하기

스캔한 PDF를 한 폴더에 모아두고 다음을 실행한다.

```powershell
python C:\ocr\compose\ocr_batch.py "C:\ocr\input"
```

문서마다 별도 프로세스로 돌기 때문에 한 권이 실패해도 나머지는 계속 처리한다.
페이지 수가 적은 것부터 처리하므로 설정 문제가 있으면 가장 싼 문서에서 먼저 드러난다.
로그는 `ocr_output/batch_logs/`에, 전체 결과는 `ocr_output/batch_status.json`에 남는다.

이 스크립트가 모르는 옵션은 그대로 각 문서의 실행에 넘긴다. 예를 들어 `--debug-lines`,
`--fast`, `--no-cache`, `--batch 5`를 폴더 단위로 쓸 수 있다.

```powershell
python C:\ocr\compose\ocr_batch.py "C:\ocr\input" --debug-lines
```

`--debug-lines`는 일반 실행과 별개로 취급한다. 상태와 보고서, 배치 요약이 각각
`_auto_debug_status.json`, `_auto_debug_report.json`, `batch_status_debug.json`으로
따로 기록되므로, 일반 실행이 이미 끝난 폴더에서도 건너뛰지 않고 테두리 확인본을 만든다.
반대로 일반 실행은 테두리 확인본이 있어도 영향을 받지 않는다.

같은 명령을 다시 실행하면 끝난 문서는 건너뛰고 실패한 문서만 다시 처리한다.
문단 OCR 캐시가 남아 있으므로 재실행은 처음보다 훨씬 빠르다. 따라서 실패를 고친 뒤에는
같은 명령을 한 번 더 실행하면 된다.

권장 순서는 다음과 같다.

1. `ocr_batch.py`로 폴더 전체를 처리한다.
2. 실패한 문서가 있으면 원인을 고치고 같은 명령을 다시 실행한다.
3. `audit_ocr_quality.py`에 폴더를 넘겨 전체 품질표를 확인한다.

```powershell
python C:\ocr\compose\audit_ocr_quality.py "C:\ocr\input\ocr_output"
```

### 스캔할 때 유의할 점

인식 모델이 아는 문자만 나온다. 키릴 문자가 주인 책은 모델을 추가해야 한다.
위 "어떤 글자를 읽을 수 있나"를 먼저 확인한다.

검증에 실패하면 최종 PDF를 만들지 않고 `.partial.pdf`만 남긴다. 이는 설계된 동작이다.
기존에 잘 만들어 둔 결과를 덮어쓰지 않기 위해서다. 실패 사유는 보고서에 남는다.

### 유실 보완 CPU 준비

유실 보완의 원본 줄 탐지는 기존 CPU 설정 범위에서 최대 4개 작업자로 실행된다.
완료된 재개 항목은 다시 인식하지 않고, 작업자 오류·메모리 부족 시 해당 위치부터
순차 복구한다. 기존 명령으로 적용되며 `--cpu-workers 0`으로 해제할 수 있다.
세부 범위와 실측/복구 방법은 `REPAIR_CPU_PREPARATION.md`를 참고한다.
GPU 사용률 100% 유지를 보장하는 설정은 아니다.

### 잘린 경계의 인식 대기

경계 보완은 GPU 요청 하나와 다음 블록/페이지의 CPU 준비를 겹친다. 입력 PNG·모델·
문자 보존 검사·페이지 저장 순서는 유지한다. 기존 명령으로 사용하며 `--no-prefetch`로
경계/유실 보완 및 line-ocr의 해당 겹치기를 해제한다. `BOUNDARY_PREFETCH.md`를 참고한다.
