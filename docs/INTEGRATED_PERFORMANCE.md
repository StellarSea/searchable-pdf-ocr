# 통합 실행과 남은 인식 안정성 문제

## 새 캐시 전체 실행

2026-09-14, 기존 유휴 서버에서 같은 32페이지 표본을 새 출력 폴더로 처음부터 인식했다.
운영 PDF/SQLite/모델/서버 설정은 변경하지 않았다.

- 총 CLI 시간 217.620초, 모니터 포함 219.978초, 종료 코드 0.
- 본문 OCR은 4요청/동시 최대 2개, 약 81.3초였다. 과거 53.1초보다 느렸으며,
  이 단계의 모델/코드 설정은 이번 검증 병렬화에서 바꾸지 않았다.
- CPU 준비는 상한 16/실제 풀 5개로 32페이지 전부 처리, 순차 복구 0회.
- GPU 선행 공급은 32요청/736이미지, 최대 2개 대기, 오류 0회.
- 최종 검증은 실제 8개 작업자로 32페이지 전부 검사, 순차 복구 0회,
  관측 작업자 RSS 최고 약 3.57GiB.
- 최종 상태는 `completed_with_warnings`이며 `validation_failed=False`다.

과거 전체 실행 305.256초와 비교하면 이번 실행은 짧았지만, 호스트 가용 RAM과 외부 CPU 부하,
OS 캐시 조건이 달랐다. 본문 OCR도 더 느렸다. 따라서 전체 시간 차이를 전부 코드 효과로
주장하지 않는다. 특정 단계의 효과는 `REPAIR_PREFETCH.md`와 `PARALLEL_VERIFICATION.md`의
교차 비교를 사용한다.

## 최종 결과는 과거 새 인식과 완전히 같지 않았다

`tools/compare_completed_ocr.py`로 원본 해시를 확인하고 두 완료 PDF/보고서를 읽기 전용 비교했다.

- 화면 픽셀 차이: 없음.
- 글자/글자 좌표 차이: 표본 1, 3, 5, 14, 15, 22, 32페이지.
- 페이지별 보고서 차이: 표본 1, 22페이지. 줄 판정도 완전히 같지는 않다.
- 비교 도구는 이를 통과로 숨기지 않고 **종료 코드 1**과 차이 목록을 남겼다.

원시 자료: `tmp/performance-max/integrated-comparison.json`,
새 진단 PDF/DB: `integrated-output/`, 자원 표본: `integrated-profile/`.

## 차이 발생 단계 분리

1. 보완 인식 전 문자열(`repair_audit.original`)로 되돌려 비교해도 원문 문단 OCR의
   표본 1, 3, 5, 14, 15, 22, 30, 32페이지가 이미 달랐다. 공백/수식 표현만 다른 경우뿐 아니라
   숫자와 코드 문자가 달라진 경우도 있었다.
2. 두 실행에서 공통인 줄 이미지 해시 771개의 인식 응답은 전부 같았다.
3. 새 실행의 문단 레이아웃과 줄 캐시를 고정한 뒤 CPU 준비/HTTP 선행 공급을 끄고
   순차 overlay를 재생성했다. 새 병렬 실행의 PDF와 픽셀·글자·좌표가 정확히 같았다.
4. 같은 고정 입력/결과를 수정 전 검증기와 새 8작업자 검증기로 검사한 보고서도 정확히 같았다.

따라서 이 표본의 차이를 새 **하류 배치/검증 스케줄링**이 만들어 낸 것으로 보지는 않는다.
원문 문단 OCR 응답 단계에서 발생한 변동이 이미 입력에 포함되어 있었다.
이는 반복 실행의 전체 인식 정확도가 유지됐다는 증거가 아니며, 변동의 세부 원인은
아직 규명하지 않았다. 모든 변동을 서버의 무작위 샘플링 때문이라고 단정하지 않는다.

고정 입력 재현: `tmp/performance-max/integrated-fixed-input-replay/comparison.json`.
발생 단계 정리: `tmp/performance-max/upstream-analysis.json`.

## 원본으로 확인한 실제 오류

표본 3페이지의 수식 상수는 원본에 **17**로 인쇄되어 있다. 과거 문단 OCR은 17,
이번 새 문단 OCR은 1로 인식했다. 원본 crop
`tmp/performance-max/upstream-review/page3-block4.png`를 렌더링해 직접 확인했다.

픽셀/문자 보존 검증은 "OCR이 반환한 글자를 PDF에 빠뜨리지 않고 넣었는가"를 검사한다.
그 자체로 OCR이 원본의 글자를 정답으로 읽었음을 보장하지 않는다. 이번 사례가 그 한계를
보여준다. 이 진단 결과를 정확도 개선이 확인된 결과로 운영 출력에 대체하지 않았다.

## 남은 우선 작업

성능 최대화 목표를 완료로 처리하지 않는다. 원문 문단 OCR의 반복 변동, 특히 숫자/코드
누락의 원인을 먼저 확인하고 성능과 함께 평가해야 한다. 모델 설정 변경이나 인식 반복을
추가한다면 속도와 정확도 영향을 별도 측정해야 한다. 기존 원문 캐시는 그대로 보존한다.
