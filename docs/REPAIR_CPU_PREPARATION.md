# 유실 보완 CPU 준비: 운영 연결

## 적용 범위와 복구

`compose/ocr_repair_prepare.py`가 보완 단계의 원본 줄 탐지를 최대 4개 독립 프로세스로 준비한다.
각 작업자는 별도 PyMuPDF 문서를 읽고 좌표만 반환한다. 부모는 기존 페이지/블록 순서대로
PNG를 만들고 OCR 응답을 판정·중간 저장한다. GPU 요청 수, 모델, 렌더링 배율, 검출 임계값,
원본/PNG 캐시 키와 출력 이름은 바꾸지 않는다. HPS는 사용하지 않는다.

- CLI의 기존 `--cpu-workers 16` 상한 중 이 단계는 실측한 최대 4개만 사용한다.
  overlay의 상한 16개와 검증의 상한 8개는 그대로이며 세 CPU 풀은 단계별로 실행된다.
- `--cpu-memory-mb 16384` 예약 예산, 가용 메모리의 절반, 시스템 예비량 2 GiB를 함께 고려한다.
  모든 작업자의 기본 예약량과 가장 큰 페이지 하나를 처리할 여유로 풀 크기를 정한다.
  실행할 페이지마다 추가 예약량을 합산해 입장시키므로, 큰 페이지 하나 때문에 작은 페이지까지
  모두 작업자 하나로 처리하지 않는다. 시작 시 정한 총 입장 용량을 넘겨 제출하지 않는다.
- 예약량은 작업자당 512 MiB + 원본 이미지 디코딩 추정의 2배 + 최대 crop 셀 수의 12배다.
  이는 보수적인 입장 추정과 실행 중 RSS 검사이며 **OS 강제 메모리 상한은 아니다**.
- 시작은 첫 실제 탐지까지 지연한다. 완료된 재개 항목은 탐지·계획 대상에서 제외한다.
  적격 페이지가 2개 미만이거나 메모리가 부족하면 풀을 시작하지 않는다.
- 실행 중 페이지 수는 작업자 수 이하이고, 완료됐지만 아직 소비하지 않은 좌표를 포함한 대기 창은
  작업자 수의 2배다. 완료된 페이지는 래스터 예약량을 반환하고 좌표만 보관한다.
  작업자는 16페이지마다 교체하고 페이지 대기는 최대 120초다.
- 작업자 초기화/사망/잘못된 식별자·좌표/시간 초과/메모리/부분 제출 실패는 해당 풀을 회수한 뒤
  **현재 블록부터 순차 복구**한다. 같은 실행에서 다시 풀을 시작하지 않는다.
- 빈 탐지 결과는 원래 소유자 위치에서 다시 탐지한다. 체크포인트 쓰기 실패·사용자 중단은
  CPU 오류로 숨기지 않고 전달한다. 부모 소유의 이전 HTTP 결과 처리 규칙은 유지한다.

기존 명령 그대로 적용된다. 문제가 있으면 `--cpu-workers 0`으로 CPU 준비를 해제한다.
이 옵션은 기존 overlay CPU 준비도 함께 해제하며, 현재 CLI의 검증 작업자 수도 0이 된다.
`--no-prefetch`는 HTTP 겹치기 옵션이고 이 CPU 풀을 해제하는 옵션은 아니다.
라이브러리 `repair_blocks()`의 기본값은 기존처럼 순차(`cpu_workers=0`)다.

연결 전 진입점은 `tmp/performance-max/repair-cpu-rollback/ocr_to_searchable_pdf.py`에 보관했다.
우선 플래그로 복구하고, 이후 수정까지 덮어쓸 수 있는 파일 전체 복원은 차이를 확인한 뒤 수행한다.
원본·운영 캐시·기존 결과는 삭제하거나 이관하지 않았다.

## 정확도/복구 검증

`tests/test_ocr_repair_cpu.py`의 9개 회귀가 통과했다. 회전/crop/주석 표본에서 실제 작업자
2개와 4개의 탐지 좌표·PNG 바이트·보완 텍스트·수락/거절·체크포인트·원본 PDF 바이트가 같다.
완료/부분 재개, 작업자 오류·실제 강제 종료, 저메모리, 시간 초과, 초기화 실패, 부분 제출 실패,
잘못된 반환값, 빈 탐지 재시도, 체크포인트 오류·중단과 40페이지 작업자 교체도 검사한다.

실제 책의 고정 32페이지와 기록 응답 9개를 사용한 운영 경로 교차 비교:

| 조건 | 2회 시간 | 중앙값 |
|---|---|---:|
| 순차 CPU + 같은 HTTP 겹치기 | 32.193 / 36.434초 | 34.313초 |
| 실제 CPU 4개 + 같은 HTTP 겹치기 | 9.719 / 9.631초 | 9.675초 |

이 표본의 **보완 준비·기록 응답 재생 단계 약 71.8% 단축**이다. 시작·계획·풀 회수 포함.
405개 탐지, 9개 PNG, 최종 보완 텍스트/판정/체크포인트가 네 번 모두 같았고 순차 복구는 없었다.
새 모델 추론은 포함하지 않아 전체 OCR 속도나 새 인식 정답률의 수치가 아니다.
실제 GPU를 포함한 직전 standalone 실험은 같은 단계 약 33% 단축이었다.

전체 오프라인 회귀 223개가 177.155초에 통과했고, Python 파일 84개/구현 모듈 24개의
문법·미정의 전역·순환 의존성 검사도 통과했다. 보완 재생 결과는 기준 DB에 저장된 실제
`source_pruned.json`과도 전체 JSON 해시가 같았다.

원시 자료: `tmp/performance-max/repair-cpu-production-offline/`.
보고서 `repair_cpu_stats`에는 초기/캐시 재보완별 실제 작업자·준비 페이지·복구 사유를 기록한다.
`admission_capacity_mib`, `peak_reserved_mib`, `peak_running_pages`로 페이지별 입장을 확인한다.
기존 `per_worker_reservation_mib`는 호환성을 위해 최대 페이지의 전체 예약 추정치를 계속 기록한다.
이미 완료된 캐시를 사용하는 실행은 보완을 다시 하지 않으므로 이 목록이 비어 있을 수 있다.

```powershell
python -m unittest discover -s tests -p test_ocr_repair_cpu.py -v
python tools/benchmark_repair_pool.py --source tmp/cpu_workers/production32/source.pdf --baseline tmp/performance-max/low-host-load-full-output --out tmp/NEW-repair-cpu --workers 0 4 --repeats 2 --prefetch --production
```

`--live`는 실제 GPU OCR 요청을 추가한다. 읽는 기준 DB는 mode=ro이며 새로운 진단 폴더만 만든다.
GPU 100% 유지와 전체 책 정답률은 보장하지 않는다. 동일 입력에서 관측된 기존 VLM 응답 변동은
이 CPU 구조 변경과 별도로 남아 있으며 새 인식의 문자 차이는 숨기지 않고 비교해야 한다.

## 큰 페이지가 섞인 책의 입장 개선 (2026-09-14)

사용자가 `1/16 workers (stage cap 4)`를 보고한 실행에서, 살아 있는 보완 작업자 표본은
한 코어 기준 약 84~100%를 사용했다. GPU 10개 표본 중 9개는 0~4%, 하나는 37%였다.
이 구간에서는 CPU 줄 탐지가 다음 요청 공급을 제한했다. 실행 중인 프로세스와 서비스를
중단하거나 다시 시작하지 않았으며, 이 Python 수정은 다음 클라이언트 실행부터 적용된다.

해당 책의 적격 페이지 393개는 예약 추정 중앙값 892 MiB, 최대 2,297 MiB였다.
이전 계산은 `작업자 수 × 최대 페이지 예약량`이었다. 이제 `모든 작업자 × 512 MiB`에
실행 중인 각 페이지의 추가 예약량을 더한다. 동일한 입장 용량과 시스템 예비량을 유지하며
페이지 크기에 따라 동시 실행 수를 줄인다. 시작 후 자동으로 풀 크기를 늘리는 변경은 아니다.

실제 책에서 큰 마지막 페이지를 포함한 고정 32페이지, 기록된 보완 응답 24개로 교차 비교했다.
입장용 가용 메모리 입력을 양쪽 모두 10 GiB로 고정하여 실제 입장 용량은 4 GiB였다.
이는 실험용 메모리 입력이며 당시 OS의 가용 메모리를 의미하지 않는다.

| 구현 | 실제 작업자 | 두 번의 시간 | 중앙값 |
|---|---:|---|---:|
| 이전 최대 페이지 기준 | 1 | 39.395 / 45.691초 | 42.543초 |
| 페이지별 합산 입장 | 4 | 18.660 / 19.695초 | 19.177초 |

이 표본의 보완 단계는 약 55% 단축됐다. 탐지 345개, PNG 24개, 텍스트, 수락/거절,
체크포인트가 네 번 모두 같았다. 양쪽 모두 빈 탐지의 원래 위치 재검사 2회, 풀 오류 복구 0회였다.
새 구현의 최고 예약 합계는 4,053 MiB로 용량 4,096 MiB 안에 있었고,
측정한 작업자 합계 RSS 최고는 약 1,246 MiB였다.

측정에는 계획·CPU 준비·PNG 생성·기록 응답 적용·풀 회수가 포함된다. 새 GPU 추론은 없고,
사용자의 다른 OCR 단계가 함께 실행 중이었으므로 전체 OCR 속도나 정답률 개선 수치로 쓰지 않는다.
자료는 `tmp/repair-weighted/comparison.json`, 재현 스크립트는 같은 폴더의 `benchmark.py`다.
해당 폴더의 이전 구현과 입력 스냅샷도 보관한다. 회귀에는 큰 마지막 페이지, 예약 합계 제한,
완료된 래스터 예약 반환과 완료 좌표 대기 창 제한을 추가했다.
관련 회귀 11개와 전체 오프라인 회귀 260개(203.905초)가 통과했다.
문법·미정의 전역·순환 의존성 검사도 Python 파일 91개/구현 모듈 24개에서 통과했다.

## 실제 전체 실행

새 출력 폴더의 32페이지 OCR은 CLI 180.568초, 모니터 포함 183.096초에 완료됐다.
보완 CPU는 시작 시 메모리 입장 판단으로 실제 2개, 32페이지 준비/빈 결과 재시도/순차 복구 0회였다.
합산 작업자 RSS 최고 약 684 MiB. overlay는 실제 5개, 최종 검증은 실제 8개를 사용했고
이들 단계도 순차 복구가 없었다. 운영 보고서 `repair_cpu_stats`까지 정상 게시됐다.

| 로그 구간 | 직전 낮은 호스트 부하 실행 | 이번 실행 |
|---|---:|---:|
| 본문 | 약 70.90초 | 약 85.22초 |
| 유실 보완 | 약 41.66초 | 약 29.63초 |
| 경계 보완 | 약 27.58초 | 약 27.22초 |
| overlay | 약 27.01초 | 약 31.85초 |
| 검증/게시 | 약 6.29초 | 약 6.51초 |

전체 시간은 173.629 → 180.568초로 오히려 늘었다. 이번 한 번의 결과를 전체 속도 개선으로
표시하지 않는다. 보완 단계는 짧아졌지만 본문/overlay 시간과 메모리 여유가 달랐다.
정확한 함수별 타이머가 아니라 인접 저장/초기화도 포함한 로그 경계의 근삿값이다.

32페이지 화면 픽셀과 페이지별 품질 finding은 모두 같았다. 최종 글자/좌표는 3·11·15페이지,
line decision 기록은 달라 엄격한 기존 결과 동일성 비교는 **실패(exit 1)**로 기록했다.
이 세 페이지는 보완 전 문단 문자열부터 달랐고 문단 박스는 같았다. 공통 원시 줄 이미지
응답 771개는 모두 같았다. 이는 새 인식 변동의 위치를 좁히지만 정답률을 증명하지 않는다.
기록 응답을 고정한 앞선 CPU A/B와 이 새 모델 실행은 구분한다. 기존 미배정 상자 경고 48개는 남는다.

신선한 보완 GPU 표본 29개 중 ≤10%는 11개이고, 그중 10개에서 VLM 실행/대기 요청이 없었다.
CPU 병렬화로 GPU 저사용 구간을 없앤 것은 아니다. Windows GPU 기록에서 Chrome 3D 최고 3%,
WSL VM 3D 최고 93%였다. 본문 중 별도 시점에 VRAM 15,838/16,303 MiB와
Windows 공유 GPU 메모리 약 0.75 GiB도 관측했다. 메모리 압박은 추가 검증할 가설이며
이 기록만으로 느려진 원인을 확정하지 않는다. VRAM 예약 0.8과 서버/OS 설정은 그대로다.

원시 자료는 `tmp/performance-max/repair-cpu-production-full-output/`,
`repair-cpu-production-full-profile/`, `repair-cpu-production-full-comparison.json`,
`repair-cpu-production-input-variation.json`에 있다. 다음 검증 대상은 호스트/VM/VRAM 여유를
통제한 전체 반복과 본문·경계 보완에서 GPU 공급이 비는 구간이다.
