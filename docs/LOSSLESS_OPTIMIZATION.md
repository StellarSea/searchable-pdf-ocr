# 정확도 보존 최적화 (2026-09-13)

인식 모델, 입력 폭 320, GPU 작업자 기본값 1, 렌더링 배율, 검출 임계값,
원문 보존/숫자 검사, 최종 전 페이지 검증을 그대로 유지했다.
이번 변경은 더 적은 픽셀로 인식하거나 검증을 생략하는 방식이 아니다.

## 적용된 변경

1. 줄 이미지 전처리: 전체 잉크 픽셀의 좌표 목록을 만들지 않고 행/열 존재 여부로
   같은 경계를 구한다. float64 grayscale을 한 번만 계산하여 줄/조각에서 재사용한다.
   잘라낸 RGB 픽셀, 여백 2px, 공백 분할점과 재결합 구분자는 기존과 동일하다.
2. 줄 탐지 결과 캐시: 원본 SHA, 페이지, cropbox/mediabox/회전, 주석,
   PyMuPDF 버전/안티앨리어싱, 모든 숫자 설정, 구현 파일 해시, 문단 좌표로 식별한다.
   유효한 빈 목록은 재사용하지만 렌더 실패와 손상된 좌표는 재시도한다.
3. 경계 복구 저장: 성공한 페이지 하나씩 원자적으로 저장하고 전체 JSON은
   성공적으로 끝났을 때 한 번만 내보낸다. 중간 실패는 완료 페이지부터 재개한다.
4. 검증 및 조회: 페이지 텍스트 추출을 한 번만 하며 모든 기존 검증 항목을 유지한다.
   줄 응답 색인/응답의 SQLite 조회도 JOIN 한 번으로 합쳤다.
5. HTTP 응답성: GPU 작업 풀과 별도의 단일 조정 작업자를 사용하여 인식이
   이벤트 루프를 막지 않는다. 추론 요청 1개 + 대기 1개로 제한하며 초과는 429,
   시작 중에는 503이다. 클라이언트는 동일 요청을 1초/2초 뒤 최대 두 번 재시도한다.
   취소된 요청의 GPU 작업이 끝나기 전에는 자리를 다시 내주지 않는다.

## 측정 결과와 범위

실제 책에서 추출한 두 표본, 총 24개 문단/119줄(한글 및 영문)을 사용했다.
같은 컨테이너, 같은 로드된 모델에서 변경 전/후를 번갈아 3회 실행했다.
아래 줄 인식 값은 각 문단별 중앙값의 합이다. 모델 로딩, HTTP, PDF 렌더링/저장,
문단 OCR을 포함하는 **전체 PDF 처리 시간은 아니다**.

| 측정 항목 | 이전 | 이후 |
|---|---:|---:|
| 컨테이너 전처리만, 119줄 중앙값 | 1.326초 | 0.453초 |
| 줄 인식 전체 (전처리 + GPU 추론 + 조립) | 1.695초 | 0.857초 |
| 위 인식 중 전처리 | 1.315초 | 0.468초 |
| 위 인식 중 GPU 예측 | 0.380초 | 0.385초 |
| 6/7/166페이지 줄 탐지, 19블록 | 5.434초 | 첫 캐시 5.290초 / 재사용 0.016초 |

줄 인식 단계는 약 49.4% 단축됐다. 이 비율을 전체 OCR에 그대로 적용하면 안 된다.
마지막 줄은 탐지에 한정한 단일 실행 표본이며, 기존 OCR 응답 캐시와 별개의 효과다.
Windows CPU 측정도 119줄 전처리 3.245초 -> 1.078초였으나 다른 검증과 동시에
실행한 보조 측정이다. 주 성능 판단은 동일 컨테이너의 교차 비교를 사용한다.

## 정확도 검증

- 119줄의 모든 분할 이미지 픽셀, 조각 수, 공백 구분자가 변경 전/후 정확히 같았다.
- 같은 GPU 모델에서 3회씩 비교한 인식 문자열, 순서, 신뢰 점수가 모두 같았다.
- 반영 후 실제 HTTP 서비스도 기존 작업자 1개 기준 결과와 119줄 전부 일치했다.
- 실제 6/7/166페이지: 156개 줄의 좌표, 글자/글자 좌표, 렌더 픽셀, 이미지 캐시 키,
  배치 결정과 보고서가 리팩토링 이전 기준과 동일했다. 6/7페이지 목차 PNG도 확인했다.
- 새 탐지 캐시의 최초/재사용 결과 19블록/156줄도 기존 좌표와 동일했다.
- 무작위/임계값/잡음/공백 입력 100개, 실제 캐시를 사용하는 overlay의 글자/픽셀,
  렌더 오류 재시도, 원본/설정 변경, 손상된 캐시, 실패 후 재개와 요청 취소를 테스트한다.
- 전체 오프라인 회귀 테스트 95개 통과(53.378초), Python 파일 38개 문법 검사와
  구현 모듈 14개 순환 의존성 검사 통과. `git diff --check`도 통과했다.
- 반영된 서버에서 24개 이미지를 인식하는 동안 상태 요청 3회가 모두 응답했다
  (최대 0.106초). 소규모 응답성 확인이며 동시 사용자 부하 시험은 아니다.

표본에서 정확도 저하는 없었지만 전체 책의 모든 글자가 정답이라는 뜻은 아니다.
새로운 인식 모델이나 정답 교정은 하지 않았으므로 정확도 상승률도 주장하지 않는다.
기존 CHAPTER 경계 복구와 원문 보존 규칙은 유지된다.

## 캐시 호환성과 운영

- 기존 응답 키, 수동 검토 키, 모델 이름과 `boundary-ink-v3`는 유지한다.
- 줄 JSON에 `detections`, 자동 모드 SQLite에 같은 이름의 테이블을 추가했다.
  기존 캐시는 지우지 않고 그대로 읽으며 새 탐지 정보만 채운다.
- 경계 캐시 `*_boundary_cache.json`의 형식은 그대로다. 같은 위치의
  `*_boundary_cache.json.pages/<identity SHA>/<page index>.json`에 중간 저장한다.
  이전 프로그램도 성공 후 내보낸 전체 JSON을 읽을 수 있다. 새 프로그램은
  중단된 작업의 페이지별 저장본까지 재사용한다. 원시 OCR 캐시는 수정하지 않는다.
- `organize`는 경계 JSON과 페이지별 디렉터리를 모두 이동한다. 충돌하면 둘 다 보존하고
  중지한다. 작업 잠금 없이 운영 캐시 폴더를 임의로 옮기면 안 된다.
- 새 보고서의 `detection_cache_stats`는 hits/misses다. 인식 이미지의 기존
  `line_cache_stats`와 별개이다. `requestSeconds`는 이제 디코딩과 내부 대기를 포함한다.
  `queueSeconds`, `decodeSeconds`, 기존 `splitSeconds`, `predictSeconds`로 구분한다.
  HTTP 업로드/JSON 파싱 이전 시간과 응답 전송은 서버 타이머에 포함하지 않는다.
- 유휴 상태를 확인하고 줄 서비스만 다시 시작하여 반영했다. VLM/문단 서비스는
  재시작하지 않았다. 다음 실행부터 자동 적용되며 완료된 파일을 강제로 재처리하지 않는다.

## 이번에 켜지 않은 최적화

아래는 1차 최적화 완료 시점의 범위다. 후속 요청으로 구현한 한 문단 선행 준비는
`PREFETCH_PIPELINE.md`에 기록했다. PDF 프로세스를 늘리는 대신 HTTP 대기만 추가
스레드에 맡겨 동일한 단일 PDF 소유권을 유지한다.

여러 프로세스가 다음 PDF 문단을 미리 렌더링하는 CPU/GPU 파이프라인은 아직 적용하지
않았다. 요청 처리와 상태 응답의 분리는 적용했지만, PDF 렌더링과 GPU OCR의 겹쳐 실행은
별개이다. 이 기능에는 독립 PDF 소유 프로세스, 제한된 메모리 큐, 순서/캐시 키의 추가
검증과 최적화 후 병목 재측정이 필요하다. PyMuPDF를 여러 스레드에 공유하거나 GPU
작업자 수를 늘리는 방식으로 대체하지 않았다.
