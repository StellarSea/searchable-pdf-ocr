# 보완 OCR의 페이지별 CPU 탐지 풀 실험

## 상태

이 문서는 **운영 연결 전 분리 실험의 기록**이다. 이후 안전한 운영 연결은
`REPAIR_CPU_PREPARATION.md`에 정리했다. 아래의 standalone 실험은 계속 재현할 수 있고,
`tools/benchmark_repair_pool.py --production`으로 새 운영 경로도 측정할 수 있다.
GPU 모델/서버 설정, OCR 해상도/임계값, 운영 캐시와 출력물은 변경하지 않는다.

직전 낮은 호스트 부하 전체 실행에서 보완 단계는 약 41.7초였고 GPU 저사용 표본에는
VLM 실행/대기 작업이 없었다. 이번에는 같은 실제 32페이지, 기록된 OCR 응답 9개를 재생했다.

## 함수별 측정

단독 cProfile 실행은 29.008초였다. 아래 누적 시간은 서로 중첩되므로 더하지 않는다.

| 함수/단계 | 누적 시간 |
|---|---:|
| `detect_lines` 405회 | 26.089초 |
| display-list 렌더링 414회 | 18.259초 |
| NumPy reduce | 4.088초 |
| 후보 PNG 인코딩 9회 | 2.553초 |
| `_long_runs` 810회 | 2.445초 |

즉, 이전 긴 획 탐지 최적화 뒤에도 실제 픽셀 렌더링과 전체 줄 탐지가 주요 CPU 비용이다.
서로 독립인 페이지를 각 프로세스의 독립 PyMuPDF 문서로 처리해 이 작업을 나눴다.

## 구조와 제한

- 부모가 기존과 같은 유효 블록 사각형을 계획하고, 작업자는 같은 `PageRaster`/`detect_lines`로
  좌표만 반환한다. 입력 텍스트, HTTP 호출, 판정과 체크포인트는 작업자에게 맡기지 않는다.
- 원래 보완 루프는 반환 좌표를 원래 페이지/블록 순서로 읽고, 후보 PNG를 원래 방식으로 만든다.
- 작업자 상한 8, 실험 예산 8192 MiB, 호스트 여유 절반과 2 GiB 시스템 예비량을 함께 고려한다.
  최악 페이지 예약량으로 실제 풀 크기를 정하고 실행 중 RSS/가용 메모리를 확인한다.
- 대기 창은 실제 작업자의 2배, 작업자 재생성은 16페이지마다, 페이지 대기 제한은 120초다.
- 실패 시 이 실험이 소유한 풀만 회수하고 오류로 끝난다. **운영용 순차 복구가 없는 실험**이며,
  실패를 순차 계산으로 숨겨 잘못된 병렬 결과가 통과한 것처럼 보이지 않게 했다.
- 예약량/RSS 검사는 OS 강제 메모리 한도가 아니다. 더 큰 PDF/특이 이미지의 검증이 필요하다.

## 오프라인 교차 비교

0 → 2 → 4 → 8 → 8 → 4 → 2 → 0 순서로 각 2회 측정했다.
계획·프로세스 시작·탐지·후보 PNG·원래 판정/체크포인트·풀 회수까지 포함했다.

| 요청 작업자 | 실제 작업자 | 시간 2회 | 중앙값 |
|---|---:|---|---:|
| 0 | 순차 | 28.924 / 29.113초 | 29.018초 |
| 2 | 2 | 16.143 / 15.613초 | 15.878초 |
| 4 | 4 | 9.715 / 9.499초 | 9.607초 |
| 8 | 5 | 8.653 / 8.780초 | 8.716초 |

작업자 4개는 이 단계 약 66.9%, 실제 5개는 약 70.0% 단축했다. 8개가 실제 동작한
측정으로 표시하지 않는다. 작업자 합산 RSS 최고는 약 1.02 GiB였고, 최대 페이지 예약 추정은
작업자당 약 1502 MiB였다. 기록된 최고 RSS는 이 표본의 관측치이지 모든 PDF의 상한이 아니다.

8회 모두 405개 탐지 좌표, 9개 PNG 해시, 최종 보완 텍스트/수락/거절과 모든 페이지
체크포인트가 같았다. 새로운 모델 인식이나 전체 OCR 정답률 검사는 아니다.
CPU 풀 회귀 6개(독립 PDF·회전/crop/주석·입력 보존·부모 오류·저메모리·시간 초과·잘못된 페이지)가
통과했고, Python 파일 82개/구현 모듈 23개 구조 검사를 통과했다.

## 실제 보완 GPU 인식 연결

이후 같은 HTTP 겹치기를 활성화하고 0 → 4 → 4 → 0 순서로 실제 보완 인식을 실행했다.
작업자 4개는 모두 실제 4개였고, 합산 작업자 RSS 최고 약 0.90 GiB였다.

| 조건 | 시간 2회 | 중앙값 |
|---|---|---:|
| 기존 순차 CPU + HTTP 겹치기 | 36.007 / 33.715초 | 34.861초 |
| CPU 4개 + 같은 HTTP 겹치기 | 23.178 / 23.566초 | 23.372초 |

보완 단계 약 33.0% 단축. 네 실행 모두 9개 요청 PNG, 405개 탐지 좌표, OCR 응답과
판정/체크포인트가 같았다. 전체 문서 인식 정답률의 보장이나 모든 VLM 응답의 재현성 증명은 아니다.

부모가 노출된 HTTP 응답 대기를 기록한 합계는 순차 5.41/3.31초, 병렬 15.50/16.02초였다.
CPU 준비가 빨라져 기존 CPU 계산 뒤에 가려졌던 응답 대기가 더 드러난다. 이것만으로 서버의
요청 처리 자체가 느려졌다고 해석하지 않는다. 전체 보완 완료 시간은 줄었다.

신선한 GPU 표본 수/평균은 순차 35개/21.3%, 33개/16.1%, 병렬 23개/26.8%,
24개/20.2%였다. GPU ≤10%이며 VLM 지표도 신선한 표본은 순차 합계 6개, 병렬 3개였고
모두 VLM 실행/대기 0이었다. 비동기 표본 수를 정확한 유휴 초 수로 바꾸지 않으며,
GPU 100% 유지가 달성된 것은 아니다. 원시 결과는 `repair-pool-live/`,
프로세스별 GPU를 포함한 자원 표본은 `repair-pool-live-profile/`에 있다.

## 재현

```powershell
python tools/benchmark_repair_pool.py --source tmp/cpu_workers/production32/source.pdf --baseline tmp/performance-max/low-host-load-full-output --out tmp/NEW-repair-pool --workers 0 2 4 8 --repeats 2 --profile-serial
python -m unittest discover -s tests -p test_repair_pool_experiment.py -v
```

`--live --prefetch`를 명시하면 같은 HTTP 겹치기 설정으로 실제 보완 인식까지 비교한다.
입력 PNG/좌표 차이는 즉시 실패시키고, 새 모델 응답/판정 차이는 모든 결과에 남긴 뒤
동일성 실패로 종료한다. 원시 자료는 `tmp/performance-max/repair-pool-experiment/`에 있다.

## 운영 연결 전 남은 일

1. 탐지 계획의 공통 책임을 core 모듈로 분리해 정상/순차 복구 경로의 조건 중복을 없앤다.
2. 완료된 보완 페이지는 계획/풀 시작도 생략하고, `--cpu-workers 0`/기존 메모리 상한과 연결한다.
3. 오류/잘못된 결과/작업자 사망/시간 초과/메모리 압박 시 풀 회수 후 해당 위치부터 순차 복구한다.
   이미 완료된 HTTP/체크포인트를 반복하거나 원시 OCR 캐시를 덮어쓰면 안 된다.
4. 체크포인트 저장 실패와 사용자 중단은 숨기지 않고, HTTP 작업자와 CPU 풀을 함께 회수한다.
5. 더 긴 실제 문서와 기존 캐시 재개, 전체 PDF 픽셀·문자·좌표 검증 후 운영 기본 연결을 결정한다.
