# 성능 설정과 실행 구조

현재 CLI와 Compose의 작업자·메모리·선행 요청 설정을 모아 설명한다.
인식 모델·해상도·임계값을 유지하면서 준비와 대기를 겹치는 기능이다.
아래 예산은 작업 입장을 위한 추정값이며 전체 프로세스나 컨테이너의 강제 RAM 상한은 아니다.

## 호스트 CLI

| 옵션 | 기본값 | 조정 범위와 의미 |
|---|---:|---|
| `--batch` | 10 | 본문 OCR 요청의 페이지 수. `0`이면 전체 전송 |
| `--ocr-requests` | 2 | 본문 HTTP 요청을 최대 2개 겹침. `1`은 순차 |
| `--cpu-workers` | 16 | CPU 페이지 준비 상한. 논리 CPU 수·메모리에 따라 축소. `0`은 순차 |
| `--cpu-memory-mb` | 16384 | CPU 준비/검증의 메모리 예산(MiB), 최소 256 |
| `--verify-workers` | 8 | 최종 검증 작업자 상한. `0`은 순차. CPU 작업자 상한도 적용 |
| `--no-prefetch` | 꺼짐 | 줄 OCR·유실/경계 보완의 CPU/HTTP 겹치기와 GPU 선행 공급 해제 |
| `--no-gpu-prefetch` | 꺼짐 | 줄 PNG의 언어별 요청 묶기만 해제 |

메모리가 부족하면 작업자 수와 준비 예산부터 줄인다. 검증을 생략하는 `--fast`는
성능 설정과 검증 범위가 다르므로 같은 조건의 속도 비교로 취급하지 않는다.

```powershell
python run.py "input/book.pdf" --cpu-workers 2 --cpu-memory-mb 2048 --verify-workers 1
```

호스트의 병렬 준비와 선행 요청을 모두 끄고 비교하려면 다음과 같이 실행한다.
서버 내부 풀과 GPU 작업자 설정은 별도다.

```powershell
python run.py "input/book.pdf" --cpu-workers 0 --verify-workers 0 --no-prefetch --ocr-requests 1
```

`--no-prefetch`는 본문 요청 개수를 바꾸지 않는다. `--ocr-requests 1`을 별도로 지정한다.
`--batch 0`에는 본문 요청 겹치기를 적용하지 않는다. CLI와 달리 라이브러리 API는
호환성을 위해 CPU/검증 병렬화·GPU 선행 공급·본문 요청에 순차 기본값을 사용하는 경우가 있다.

## 단계별 제한과 실패 복구

| 단계 | 제한과 순서 | 실패 시 동작 |
|---|---|---|
| 본문 OCR | 미소비 요청/응답 최대 2묶음, 입력 바이트의 4배로 계산한 256 MiB 입장 예산. 원래 배치 경계·페이지 순서 유지 | 추가 선행 공급 중단 후 실패 묶음 순차 재시도. 영구 HTTP 오류·응답 형식 오류는 중단. 연속 저장된 지점부터 재개 |
| CPU 페이지 준비 | 캐시 우선, 준비 창은 작업자 수의 2배 이하. 각 프로세스가 독립 PDF를 읽고 부모가 순서대로 사용 | 작업자·메모리·시간 초과 오류는 소유 풀 회수 후 순차 복구 |
| 유실 보완 준비 | 기존 CPU 상한·예산 내 최대 4개. 재개 완료 항목 생략, 원본 stamp·페이지·사각형 식별자 대조 | 현재 블록부터 순차 복구. 이미 저장한 OCR은 재사용. 체크포인트 실패·사용자 중단은 전파 |
| 줄 GPU 공급 | 준비된 PNG만 언어별 최대 64개, 선행 요청 최대 2개, 전송 여유 포함 64 MiB 예산. 같은 이미지 중복 전송 방지 | 해당 실행의 선행 공급을 끄고 문단별 인식으로 복구 |
| 유실/경계 HTTP 겹치기 | HTTP 요청 하나와 다음 CPU 준비를 겹침. 앞 페이지 저장 성공 전 다음 경계 요청을 보내지 않음 | 원래 저장·재개 순서 유지. CPU/HTTP 작업자가 PDF·SQLite를 쓰지 않음 |
| 최종 검증 | 작업자별 독립 PDF, 대기 작업은 실제 작업자 수 이하. 부모가 원래 페이지 순서로 판정/게시 | 풀을 회수한 뒤 **모든 페이지를 순차 재검사**. 일부 결과만으로 통과 처리하지 않음 |

예산보다 큰 입력은 임의 축소하거나 다른 배치로 재분할하지 않고 순차 경로로 처리한다.
HTTP에 이미 도착한 추론은 강제로 취소할 수 없으므로 중단 시 요청 정리를 기다릴 수 있다.
선행 공급 모듈 자체는 서비스를 재시작하지 않는다. CLI의 서비스 준비/복구는 별도 동작이다.

일반 PDF의 최종 검증은 전 페이지 72dpi RGB 픽셀, 문자 및 투명 텍스트 등을 확인한다.
작은 문서나 특별한 렌더 설정은 순차 검사하며, `--debug-lines`는 픽셀 일치 검사의 대상이 아니다.
검증 작업자는 일정 페이지 수 뒤 교체하고, 메모리 압박 시에도 검사 범위를 줄이지 않는다.

## 서버 설정

현재 Compose의 기본값이다. `compose/compose.yaml`에서 `${...}`로 치환하는 값은
`compose/.env`로 조정하고, 고정된 값은 YAML에서 확인한다. 이미 실행 중인 OCR이 끝난 뒤 다음 실행에 적용한다.

| 설정 | 기본값 | 역할 |
|---|---:|---|
| `LINE_OCR_WORKERS` | 1 | 줄 GPU 모델 작업자 |
| `LINE_OCR_INPUT_WIDTH` | 320 | 줄 인식 입력 폭. 정확도에 영향을 주므로 단순 속도 조절용으로 바꾸지 않음 |
| `LINE_OCR_BATCH_SIZE` | 32 | 줄 서버 내부 추론 배치 |
| `LINE_OCR_CPU_THREADS` | 8 | 줄 모델의 CPU 스레드 |
| `OCR_PDF_WORKERS` | 4 | 문단 API의 PDF 디코딩 spawn 풀. `0`은 기본 순차 reader |
| `OCR_PDF_MEMORY_MB` | 8192 | 공유 출력·최종 배열·작업자·입력 버퍼 예약 예산(MiB) |
| `OCR_PDF_TIMEOUT` | 60 | 풀 초기화와 한 요청의 병렬 페이지 준비에 각각 적용하는 제한(초) |

서버 PDF 준비는 `ocr_server_entrypoint`에서 원래 reader를 확보한 뒤 연결한다.
작업자마다 PDFium 문서·폼을 독립적으로 소유하며 GPU 모델을 생성하지 않는다.
부모만 공유 메모리를 생성·해제하고, 결과를 일반 NumPy 소유 배열로 복사한 후 모델에 전달한다.
모든 페이지 출력을 한꺼번에 할당하지 않고 제한된 창에서 회수·해제한다.

작은 PDF, 페이지 수 제한 초과, 메모리/공유 공간 부족은 순차 reader로 처리한다.
풀 실패는 terminate/join 후 공유 메모리를 해제하고 전체 요청을 기본 reader로 다시 처리한다.
해당 서버 생명주기에서는 실패한 병렬 경로를 비활성화한다. 이미지 입력이나 종료 시 풀을 회수한다.

GPU 작업자를 늘리거나 사용률을 100%에 가깝게 만든다고 처리량이 증가하는 것은 아니다.
문단 모델과 줄 모델의 경합, 렌더링, 전송, 저장 비용을 함께 확인한다.

## 측정과 진단

보고서의 `line_cache_stats`, `gpu_feed_stats`, `repair_cpu_stats`, `boundary_feed_stats`,
`verification_stats`와 서버 `[pdf-cpu]` 로그로 캐시 사용·대기·메모리·복구 사유를 확인한다.
성능 통계는 OCR 정답률이나 원본 대조 결과를 대신하지 않는다.

`tools/`의 benchmark/profile 도구는 `--help`로 입력과 출력 위치를 먼저 확인한다.
일부는 실제 OCR 서비스를 호출한다. 임시 입력·별도 출력/캐시를 사용하며 운영 작업을 재시작하지 않는다.
비교에는 같은 입력·하드웨어·모델·옵션, cold/warm cache 구분, 시간·최대 메모리와 함께
픽셀·문자·좌표·캐시 식별자 보존 여부를 기록한다. 작은 표본의 결과를 전체 책의 정확도로 확대하지 않는다.

2026-10-01의 호스트 SQLite 읽기 비교에서는 `TextArtifact.read_bytes()`의 연결을
2회에서 1회로 줄였다. Windows 11(build 26200)/Python 3.13.15,
16 논리 CPU(AMD64 Family 26 Model 68), 32개×276 KB 합성 항목, 새 프로세스의
256회 warm 읽기를 AB/BA 순서로 7회 비교한 중앙값은 0.300→0.193초,
처리량은 855→1,328회/초였다. 인터프리터·합성 자료를 포함한 프로세스 수명 최대 RSS는
33.22→33.38 MiB였으며 항목 바이트와 SHA-256 검사는 같았다.
OS의 물리 cold cache와 실제 OCR 처리량은 측정하지 않았다.
