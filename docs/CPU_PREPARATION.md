# 운영 CPU 페이지 준비

자동 OCR의 CLI 기본값은 **CPU 작업자 최대 16개**다. 실제 동시 작업량은 논리 CPU 수,
페이지 수, 캐시 상태, 메모리 예산에 따라 줄어든다. GPU 작업자 수/모델/입력 폭은 바꾸지 않는다.
기존 순차 렌더링, HTTP 재시도, 문자 보존, 검증 후 게시 경로는 복구 수단으로 유지한다.

## 사용법과 호환성

기존 명령 그대로 사용한다.

```powershell
python C:\ocr\compose\ocr_to_searchable_pdf.py "C:\ocr\input\쉽게 배
우는 C 자료구조.pdf" --debug-lines
```

| 옵션 | 의미 |
|---|---|
| `--cpu-workers 16` | 기본값. 자동 모드 CPU 준비 프로세스 수의 상한 |
| `--cpu-workers 8` | 이전 작업자 수로 줄이기 |
| `--cpu-workers 0` | CPU 준비를 기존 순차 경로로 고정 |
| `--cpu-memory-mb 16384` | 추가 CPU 준비의 메모리 예산(MiB), 기본 16384(16 GiB) |
| `--no-prefetch` | 기존 문단 단위 HTTP 선행 준비만 해제. CPU 풀은 별도 옵션 |

CPU 작업자는 0~16, 메모리 예산은 256 MiB 이상을 받는다. 메모리 예산을 낮춰도 렌더 해상도나
검출 임계값을 낮추지 않는다. 예산에 맞지 않는 페이지는 순차 경로에서 처리한다.
원래의 완전 순차 준비/HTTP 실행을 원하면 `--cpu-workers 0 --no-prefetch`를 함께 사용한다.

`--fast`, `--paragraph`, `--dump-structure`, 수동 `--line-ocr-pages` 모드는 기존 경로를 유지한다.
자동 `--debug-lines`, 목차, 경계 복구/레이아웃 검토, 폴더 배치와 중단 후 재개는 그대로 지원한다.
라이브러리 `overlay()`의 `cpu_workers` 기본값은 호환성을 위해 0이고 CLI가 명시적으로 16을 전달한다.
스케줄링 옵션은 완료 상태/원본/검토/이미지 캐시 식별자에 넣지 않는다. 기존 캐시는 삭제할 필요가 없다.

## 캐시 우선 처리

부모가 앞으로 최대 작업자 수의 2배만큼 페이지 메타데이터와 기존 탐지/응답 캐시를 확인한다.
이때는 이미지를 렌더링하지 않는다.

- 필요한 좌표와 OCR 응답이 모두 있으면 풀을 만들지 않고 캐시에서 배치를 준비한다.
- 줄 좌표가 캐시에 있어도 표의 열 경계 확인에는 직접 픽셀 조회가 필요할 수 있다. 이 경우
  해당 페이지만 기존 캐시 우선 경로에 맡기며, 문서 전체의 CPU 준비를 실패로 처리하지 않는다.
- 일부만 있으면 탐지 캐시와 이미 인식한 crop 키를 작업자에 전달한다. 작업자는 빠진 PNG만 준비한다.
- 캐시는 부모만 읽고 쓴다. 작업자는 PDF/폰트를 각각 열어 좌표·문자 분할·PNG를 반환한다.
- 결과를 페이지 순서로 소비하고, 원본/페이지/레이아웃 식별자를 확인한 뒤 사용한다.
- CPU 결과/HTTP 응답 대기 중 약 0.1초 간격 및 문단 사이에 완료된 작업을 회수하고 빈 자리를
  보충한다. 완료 결과는 따로 보관하므로 앞 페이지가 느려도 다음 준비를 진행할 수 있다.
  메모리 때문에 미뤄진 미래 페이지는 여유가 생기면 다시 제출한다.
- OCR 응답이 저장된 상태에서 실패하면 다음 실행에서도 재사용한다. 새 감사 결정은 기존처럼
  최종 검증/일반 PDF 게시 후에만 공개한다.

공유 알고리즘은 `ocr_layout.py`, 프로세스/캐시 계획/예산은 `ocr_prepare.py`가 소유한다.
기존 `_block_layout` 이름은 호환용으로 남는다. `ocr_render.py`의 탐지 알고리즘/구현 해시는
이번 변경으로 바꾸지 않아 이미 저장된 탐지 좌표도 계속 재사용할 수 있다.

## 메모리와 실패 복구

- 미회수 작업 수는 작업자 수 이하, 완료/캐시 결과를 포함한 준비 창은 작업자 수의 2배 이하다.
  현재 사용 중인 페이지는 별도로 메모리를 계산한다. 문서 전체에 대한 futures를 만들지 않는다.
- 원본 이미지 디코딩, NumPy 임시 배열, PNG/전송 복사를 추정해 페이지별 메모리를 예약한다.
  동시 예약 합계는 설정 예산과 `(현재 가용 메모리 - 2 GiB) / 2` 중 작은 값 이하로 제한한다.
- 완료 결과를 회수하면 해당 작업의 임시 배열 예약 대신 반환된 좌표/문자/PNG 객체 크기의
  2배 + 1 MiB를 보관 예산으로 계산한다. PNG를 다시 직렬화하지 않으며 실제 RSS 검사도 유지한다.
- 페이지당 PNG 보관은 64 MiB 이하다. 초과하거나 큰 단일 crop이 예약량을 넘으면 축소하지 않고 복구한다.
- 제출/결과 대기 시 가용 메모리와 추가 부모/자식 RSS를 확인한다. 예산 초과 또는 가용 메모리
  2 GiB 미만이면 이 작업이 소유한 풀만 종료하고 남은 문서를 순차 처리한다.
- 준비 결과 대기 한도는 120초다. 작업자 오류, 초기화 실패, 잘못된 결과 식별자, 시간 초과도
  풀을 종료하고 순차 처리한다. 동일 문서에서 풀을 반복 재시작하지 않는다.
- 작업자는 최대 16페이지 처리 후 교체해 장기 실행 메모리 누적을 줄인다.
- 풀 시작 시에는 현재 입장 예산으로 실행할 수 있는 페이지 수만큼만 프로세스를 만든다.
  예를 들어 16개를 요청했어도 두 페이지 분량의 메모리만 있으면 2개로 시작한다.
  작업 슬롯도 실제 풀 크기로 제한한다. 이는 16개 인터프리터가 한꺼번에 떠서
  메모리 안전장치를 발동시키고 문서 전체가 순차 처리로 내려가는 상황을 줄인다.
  이 실행 중 풀 크기는 고정이며, 다음 실행에서는 당시 메모리에 맞춰 다시 결정한다.
- 부모가 실패하거나 Ctrl+C로 중단되면 자체 풀을 종료하고 PDF/SQLite 자원을 닫는다.

**이 예산은 OS가 강제하는 메모리 상한이 아니다.** 샘플링 사이의 순간 할당, 원본 PDF 처리,
순차 복구 자체, Docker/GPU 서비스 메모리까지 제한하지 않는다. 복잡한 페이지는 기존 순차 방식에도
많은 메모리가 필요할 수 있다. 기본값을 올릴 때는 전체 가용 메모리를 함께 확인해야 한다.
`psutil`이 없는 구 환경은 순차 경로로 복구하며, 권장 설치는 `pip install -r requirements.txt`다.

보고서의 `cpu_prepare_stats`에는 실제 준비/캐시 페이지 수, 작업자 시작 수, 메모리 생략,
복구 이유, 최대 대기 수·예약량·추가 RSS를 기록한다. `peak_buffered_pages`는 최대 준비 창 크기,
`refill_jobs`는 첫 작업자 수 범위를 넘어 보충한 작업 수다. 이 항목은 정확도 판단과 분리된 통계다.
`workers`는 CPU/페이지 수를 반영한 설정 상한, `pool_workers`는 실제 시작한 프로세스 수다.
`memory_limited_pool`은 시작 시 메모리 예산으로 풀을 줄였는지 표시한다.

## 검증

`tests/test_ocr_cpu.py`는 72페이지 처리(작업자 교체 포함), 순차 출력과 픽셀/글자 좌표/결정 동일성,
완전 캐시에서 렌더/HTTP/프로세스 시작 0회, 부분 실패 후 응답 재사용, 저메모리·오류·시간 초과·
식별자 불일치 복구, 기존 옵션/완료 식별자 호환성을 확인한다.

16개/작업 보충 변경에는 17페이지를 실제 16개 프로세스로 처리하여 순차 결과의 픽셀·문자
좌표·결정과 비교하는 검사를 추가했다. 느린 첫 페이지 뒤에서의 보충, 미래 페이지의 메모리
재시도, HTTP 대기 중 소유 스레드에서만 보충하는 동작도 검사한다. 전체 오프라인 회귀
128개가 통과했다(129.502초). 이는 정확도 보존/스케줄링 동작 검사이며 실제 책의 속도 실측은 아니다.

실제 PDF/GPU 비교 도구는 다음과 같다. 원본과 운영 캐시는 읽기만 하고 새로운 진단 디렉터리에 쓴다.

```powershell
python tools/benchmark_cpu_overlay.py "input/쉽게 배우는 C 자료구조.pdf" "input/ocr_output/.ocr/쉽게 배우는 C 자료구조_boundary_cache.json" --production --workers 0 4 --rounds 1 --out tmp/cpu_workers/production-recheck
```

이제 `--production`의 캐시 재실행도 CPU 풀을 수동으로 끄지 않는다. 운영 스케줄러가 자동으로
캐시를 판별해 풀을 만들지 않아야 테스트를 통과한다. 이전 실험 기록은 `CPU_WORKER_BENCHMARK.md`에 있다.

구현 선택은 [Python multiprocessing 문서](https://docs.python.org/3/library/multiprocessing.html)와
[PyMuPDF의 프로세스별 문서 열기 지침](https://pymupdf.readthedocs.io/en/latest/recipes-multiprocessing.html)을 따른다.

### 2026-09-13 실제 32페이지 검증

아래 측정은 작업자 4개, 메모리 예산 4096 MiB 기준이다. 이후 사용자 요청으로 기본 상한을
작업자 8개, 이후 16개와 빈 작업자 보충 방식으로 변경했으며 메모리는 16384 MiB다.
아래 시간은 이전 방식의 측정이며 16개 방식의 속도 향상을 보장하지 않는다.
가용 메모리 기반 제한과 자동 순차 복구는 유지한다. 변경은 다음 실행부터 적용되며,
이미 실행 중인 작업의 풀 크기를 바꾸거나 작업을 재시작하지 않는다.

PDF 기준 6, 7, 29, 38, 66, 147, 166, 188 및 189~212페이지를 새 진단 캐시로 비교했다.
실제 GPU 줄 인식 137개 문단 요청/801개 줄 입력, 삽입 1171줄을 포함한다.

| 방식 | overlay/저장 | 최종 검증 포함 | 호스트 프로세스 트리 최대 RSS |
|---|---:|---:|---:|
| 기존 순차 준비 | 119.23초 | 133.55초 | 2.06 GiB |
| 운영 CPU 작업자 4개 | 47.08초 | 61.20초 | 3.31 GiB |

이번 단일 비교에서는 검증 포함 약 54.2% 단축했다. 전체 책 시간의 보장은 아니며,
문단 OCR/경계 복구/부분 PDF 추출/추가 기준 출력 비교는 시간에서 제외했다.
OS 파일 캐시는 통제하지 않았다. GPU 작업자는 1, 배치 32, 입력 폭 320으로 동일하다.
최대 대기 페이지 4, 최대 예약량 약 3744 MiB, 준비 페이지 32, 메모리 생략/오류 복구 0회였다.

픽셀·문자 좌표·OCR 후보/키/배치 결정·검증 보고서가 기존 방식과 동일했다.
기존 미배정 상자 49개도 동일하다(이 중 29페이지 5개). 인식/레이아웃 오류가 모두 해결됐다는 뜻은 아니다.
PDF 스킬의 시각 검증에 따라 목차 6/7페이지와 표가 있는 29페이지를 Poppler로 렌더링해 확인했다.

첫 캐시 재실행에서 표의 직접 픽셀 조회가 전체 순차 복구를 일으키는 것을 발견해 수정했다.
최종 코드는 해당 페이지만 기존 경로에 맡긴다. 진단 SQLite를 읽기 전용으로 복사해 재검증한 결과,
약 4.47초에 작업자 시작 0회·GPU 호출 0회·오류 복구 0회로 동일한 PDF가 나왔다.
31페이지는 캐시에서 준비하고 표 페이지 1개만 기존 경로를 사용했다.

원시 냉 캐시 비교: `tmp/cpu_workers/production32/comparison.json`.
최종 캐시 재개 검증: `tmp/cpu_workers/production32-warm-verified/comparison.json`.
`tools/validate_cpu_resume.py`로 같은 복사/재개 검증을 반복할 수 있다.

최종 전체 회귀 테스트는 **123개 모두 통과(95.050초)**했다. 문법/미정의 전역/순환 의존성 검사도
Python 47개 파일, 구현 모듈 16개에서 통과했다. 원본·운영 캐시·기존 최종 결과는 변경하지 않았으며
사용자의 중단된 OCR 작업이나 Docker 서비스를 재시작하지 않았다.
