# 최종 PDF 검증 병렬화

일반 자동 PDF의 최종 검증은 CPU 작업자를 기본 최대 8개 사용한다. 실제 검사는
`ocr_verify`가 담당하고, `ocr_workflow.verify`의 과거 호출 이름은 재노출한다.
OCR 모델, 입력 해상도, 줄 정렬, 원본/응답 캐시 키는 변경하지 않는다.

## 검사와 소유권

- 기존 모든 페이지의 72dpi RGB 픽셀 완전 일치, 문자 개수, 글리프 동등 치환,
  NUL 문자, 투명 텍스트 여부와 기존 삽입 오류 판정을 그대로 유지한다.
- 작업자마다 원본과 결과 PDF를 별도로 읽는다. PyMuPDF 객체를 스레드에 공유하거나
  비트맵을 프로세스 사이에 전송하지 않는다. 부모가 페이지별 검사 결과만 회수한다.
- 완료 순서는 달라도 페이지별 보고서 순서는 원래대로 유지한다. PDF/SQLite/최종 보고서
  게시는 여전히 부모 한 곳에서만 수행한다. 모든 검사가 끝나야 판정을 반영한다.
- 페이지 수/보고서의 페이지 순서/필수 검사 입력을 먼저 확인한다. 파일 크기·수정 시각·
  파일 식별자도 전후 대조해 검사 도중 바뀐 파일을 완료로 게시하지 않는다.
- 작업자는 원래 안티앨리어싱 설정을 사용한다. 그래픽/문자 AA가 다르거나 특별한
  최소 선 굵기를 설정한 경우는 설정을 바꾸지 않고 기존 순차 검사를 사용한다.

## 제한과 실패 처리

- `--verify-workers 8`이 기본이다. `--cpu-workers` 상한, 논리 CPU 수, 페이지 수,
  메모리 입장 예산에 의해 더 줄어들 수 있다. 기본 CPU 준비 상한 16개는 바꾸지 않았다.
- `--verify-workers 0`은 검증만 순차 처리한다. `--cpu-workers 0`도 검증 병렬화를 해제한다.
  라이브러리 `verify(..., workers=0)`는 호환성을 위해 순차 기본값을 유지한다.
- `--debug-lines`는 원래부터 픽셀 일치 검사를 생략하므로 가벼운 문자 검사를 순차로 유지한다.
  작은 문서(비교 페이지 면적 합 800만 픽셀 미만)도 시작 비용을 피하기 위해 순차 검사한다.
- 예산은 `--cpu-memory-mb`와 `(현재 가용 RAM - 2GiB) / 2` 중 작은 값이다. 비교용 비트맵,
  디코딩 이미지와 프로세스/캐시 여유를 페이지별로 추정하여 초기 작업자 수를 제한한다.
  실행 중에도 가용 RAM과 자식 프로세스 RSS를 확인한다. 이 값은 엄격한 OS 메모리 제한이 아닌
  보수적 입장/감시 예산이며, 단일 거대 페이지의 기존 순차 렌더링 크기를 줄이지 않는다.
- 대기 중인 작업은 최대 실제 작업자 수만큼 유지한다. 완료된 페이지의 작은 보고서만 보관한다.
  작업자 하나가 32페이지를 처리하면 교체하여 장기 실행의 네이티브 캐시 누적을 제한한다.
- 초기화/작업자/메모리/시간 초과 오류는 해당 풀을 종료·회수한 뒤 **모든 페이지를 순차 재검사**한다.
  작업자 결과 일부만으로 통과하지 않는다. 순차 검사도 실패하면 기존 최종 PDF는 보존된다.
- 사용자 중단은 삼키지 않는다. 자신이 만든 풀만 종료·회수하고 예외를 전달한다.

보고서의 `verification_stats`에는 요청/실제 작업자 수, 풀 처리/순차 처리 페이지 수,
최대 대기 작업 수, 관측 작업자 RSS, 복구 사유를 기록한다. 품질 판정과 별도인 실행 통계다.
완료/캐시 식별자는 바뀌지 않아 이미 완료한 책을 강제로 다시 인식하지 않는다.

## 실제 측정: 32페이지

기존 완료 PDF/DB는 읽기 전용으로 열고, 줄 캐시를 새 진단 DB에 복사했다. 원래 OCR 레이아웃과
복사한 캐시에서 검증 전 기대 문자 보고서를 재생성했다. 결과 PDF의 추출 문자를 기대값으로
되돌려 넣지 않았다. 재생성 PDF의 픽셀·글자·좌표가 기준 PDF와 같은지도 먼저 확인했다.
GPU/HTTP 호출은 금지하고, 수정 전 검증 코드와 새 코드의 전체 보고서를 비교했다.

정방향 실행 후 역순으로 한 번씩 교차 비교한 중앙값:

| 설정 | 실제 작업자 | 검증 시간 | 작업자 RSS 최고 |
|---|---:|---:|---:|
| 수정 전 순차 검사 | 0 | 15.958초 | 해당 없음 |
| 새 순차 경로 | 0 | 16.202초 | 해당 없음 |
| 상한 2 | 2 | 9.964초 | 약 0.93GiB |
| 상한 4 | 4 | 6.988초 | 약 1.84GiB |
| 상한 8 | 8 | 5.175초 | 약 3.57GiB |
| 상한 16 | 12 (입장 예산 제한) | 5.477초 | 약 5.24GiB |

이 PC에서는 실제 8개가 가장 빨랐다. 수정 전 대비 최종 검증 단계 약 67.6% 단축이다.
실제 16개를 실행한 결과라고 해석하면 안 된다. 모든 실행의 보고서는 정확히 같았고,
작업자 실행은 모두 32페이지 처리/순차 복구 0회였다. OS 캐시/외부 앱의 영향이 있으므로
이 수치를 전체 OCR 시간 또는 모든 문서의 속도 향상률로 확대하지 않는다.

원시 자료: `tmp/performance-max/verify-parallel/`, 자원 표본 `verify-profile/`.
수정 전 검증 코드: `tmp/verification-baseline/ocr_workflow.py`.

## 긴 실행: 320페이지

같은 실제 32페이지를 10번 반복해 작업자 교체 구간을 포함한 320페이지를 검사했다.
수정 전 165.787초, 작업자 8개 35.082초였다. 320페이지 전부 동일한 검증 보고서,
순차 복구 0회, 최대 대기 8개, 작업자 RSS 최고 약 3.58GiB를 확인했다.
한 번씩의 장기 실행 검사이며 **서로 다른 320페이지의 정확도 검증이나 전체 책 검증이 아니다**.

원시 자료: `tmp/performance-max/verify-long/`, 자원 표본 `verify-long-profile/`.

최종 오프라인 회귀 177개 통과(167.639초), 이 중 새 검증 관련 검사는 12개다.
정상/오류 검출, 순서/객체 동일성, 메모리/작업자/초기화 실패, 시간 초과/사용자 중단,
파일 변경과 부분 판정 미게시, 디버그/작은 문서/특수 AA 설정의 순차 경로를 검사한다.

## 재현

```powershell
python tools/benchmark_verify.py --source tmp/cpu_workers/production32/source.pdf --baseline-dir tmp/performance-max/baseline-output --cache-db tmp/performance-max/candidate-startup/lines.sqlite3 --baseline-module tmp/verification-baseline/ocr_workflow.py --out tmp/new-verify-comparison --repeats 2
```

새 폴더를 지정해야 한다. `--workers 8 --repeats 1 --repeat-pages 10`을 추가하면 같은
페이지를 반복한 장기 실행 검사다. `tools/profile_ocr_resources.py --out 새폴더 --no-vlm -- ...`로
감싸면 서버에 요청하지 않고 자원 표본을 함께 기록한다.
