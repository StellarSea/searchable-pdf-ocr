# 전체 처리 성능 최적화 — 진행 중

목표는 정확도를 유지하면서 현재 PC의 CPU/GPU/메모리/디스크를 효율적으로 사용해
전체 OCR 시간을 줄이는 것이다. 사용률을 올리기 위한 무의미한 부하를 추가하지 않는다.
HPS는 재도입하지 않는다. 모델·해상도·인식 임계값·원본/캐시 식별자는 유지한다.

## 2026-09-14 기준 측정

환경: Ryzen 7 9700X(8코어/16스레드), RTX 5080(16GB), 호스트 RAM 약 64GiB.
Docker VM은 16 CPU / 약 31.2GiB 상한. 기존 HYDRA 전원 계획은 변경하지 않았다.
32페이지 표본은 목차·표·수식·코드가 있는 기존 진단용 `source.pdf`다.

- 완전한 새 진단 출력의 전체 실행: CLI 305.3초, 모니터 포함 306.97초.
- 본문 OCR 4요청(동시 상한 2): 53.1초. 클라이언트 분할 준비 0.32초.
- 이후 유실/경계 보완, line-ocr/overlay, 최종 검증을 모두 수행했다.
- 호스트 가용 RAM 최저 약 1.54GiB. Docker VM 내부는 별도 시점에
  MemAvailable 약 17.3GiB / 캐시 약 8.5GiB를 기록했다.
  서로 다른 시점의 값이며 전부 동일한 메모리 누수라고 단정하지 않는다.
- CPU 준비는 16프로세스로 시작했으나, 실제 동시 페이지는 1개였고 2페이지에서
  메모리 압력으로 풀 전체가 꺼졌다. 32페이지 중 CPU 준비는 1페이지만 완료했다.
- 이때 GPU 선행 묶음은 1요청/55줄뿐이었다. 이후는 기존 문단별 처리였다.

## 적용: 메모리에 맞춘 CPU 풀 시작

기존 페이지 입장 예산과 동일한 예약량으로 시작 가능한 프로세스 수를 계산한다.
불필요한 인터프리터 대량 시작을 피하고 실제 풀 크기로 작업 슬롯을 제한한다.
기존 메모리 안전장치·오류 복구·페이지 순서·소유 스레드·캐시 규칙은 유지한다.
상한 16개, 메모리 예산 16384MiB, `--cpu-workers 0` 복구 옵션도 그대로다.

동일한 기준 OCR/경계 결과를 읽고 새 line/detection 캐시로 32페이지를 검증했다.

- 실제 풀 4개, 준비 32페이지, 순차 복구 0회, 최대 동시 페이지 4개.
- overlay 38.75초, 최종 검증 17.85초, 합계 56.61초.
- CPU 전체 사용률 약 80% 관찰. GPU 선행 공급 35요청/728줄, 오류 0회.
- 기준 최종 PDF와 픽셀·글자·글자 좌표·페이지별 품질 판정·줄 판정이 정확히 같았다.
- CPU 관련 회귀 20개 통과(34.93초). 2개는 메모리 부족 시 풀 축소와 충분할 때
  16개 유지 동작을 새로 검사한다. 이 검사는 GPU 없이 수행한다.
- 최초 전체 실행의 overlay 구간은 로그 시각 기준 약 126.6초였지만,
  두 측정 사이 가용 RAM/OS 캐시 상태가 달라 이 차이 전체를 코드 효과로 주장하지 않는다.
  후보 56.61초는 **전체 OCR 시간**이 아니라 동일한 OCR 결과에서 시작한 overlay+검증 시간이다.

## 재현 도구와 다음 확인 사항

### 추가 적용: 유실 보완의 CPU/HTTP 겹치기

`repair_blocks`가 같은 페이지의 그리기 명령을 재사용하고, CPU에서 다음 블록을 분석하는
동안 이전 PNG 한 개를 HTTP 작업자가 인식한다. 판정/중간 저장은 소유 스레드가 처리하고,
이전 체크포인트가 성공해야 다음 요청을 전송한다. CLI 기본 적용, `--no-prefetch`로 해제한다.
경계 복구와 line-ocr 모델은 변경하지 않았다. 설계/오류 복구는 `REPAIR_PREFETCH.md`를 참고한다.

- 동일한 실제 32페이지/405블록/9요청, 순차→개선→개선→순차: 77.418 / 59.392 /
  53.533 / 76.350초. 보완 단계 중앙값 76.884→56.463초(약 26.6% 단축).
- 같은 기존 서버에 실제 인식했다. 네 실행 모두 PNG·줄 좌표·인식 문자열·판정·중간 저장이
  동일했다. 전체 OCR 시간이나 전체 책의 정답률로 확대 해석하지 않는다.
- 약 1초 GPU 표본에서 ≤10% 개수는 65→48→47→64였으나, 전체 표본 수가 함께 줄었고
  평균 사용률은 약 8%로 비슷했다. 처리 시간을 줄였지만 GPU 저사용 구간의 완전 제거는 아니다.
- 현재도 보완 후보 탐색은 405블록 전체를 단일 소유 스레드에서 분석한다. 다음 CPU 병렬화나
  기존 줄 탐지 캐시와의 안전한 공유가 남은 검증 대상이다.
- 원시 결과 `tmp/performance-max/repair-overlap-live/`, 자원 표본은
  `tmp/performance-max/repair-overlap-live-profile/`. 운영 캐시·PDF·서버 설정은 변경하지 않았다.
- 최종 오프라인 회귀 165개 통과(148.843초), 구현 모듈 20개 의존성 검사 통과.

### 추가 적용: 최종 PDF 검증 병렬화

일반 PDF는 기본 검증 작업자 8개(메모리/CPU 제한에 따라 축소)를 사용한다.
기존 모든 픽셀·문자·투명 텍스트 검사와 보고서 순서를 유지하며, 실패한 풀은 회수하고
모든 페이지를 순차 재검사한다. `--verify-workers 0`으로 해제할 수 있다.
작은 문서와 디버그 문자 검증은 순차 경로를 유지한다.

- 같은 실제 32페이지의 수정 전 검증/새 검증 상한 2·4·8·16을 정방향/역순으로 비교했다.
  실제 작업자 수는 2·4·8·12였다(16 요청은 메모리 입장 예산으로 축소).
- 수정 전 중앙값 15.958초 → 8개 5.175초. 검증 단계 약 67.6% 단축, 전체 보고서 일치.
  실제 12개는 중앙값 5.477초로 8개보다 빠르지 않았다.
- 같은 32페이지를 반복한 320페이지 장기 실행: 165.787초 → 35.082초, 모든 판정 일치,
  풀에서 320페이지 처리, 순차 복구 없음, 작업자 RSS 최고 약 3.58GiB.
- 기대 문자는 원래 OCR 레이아웃/복사 캐시에서 재구성했으며 결과 PDF를 정답으로 삼지 않았다.
  전체 책의 인식 정확도 검증은 아니며, 서버와 운영 캐시를 변경하지 않았다.
- 최종 오프라인 회귀 177개 통과(167.639초). 설계/메모리 제한/재현은
  `PARALLEL_VERIFICATION.md`. 원시 결과는 `tmp/performance-max/verify-parallel/`,
  `verify-long/`, 각각의 `*-profile/`.

### 도구와 남은 확인 사항

통합 새 캐시 실행은 `INTEGRATED_PERFORMANCE.md`에 기록했다. 32페이지 전체 217.620초,
CPU 준비(실제 5개)와 검증(실제 8개)은 모두 순차 복구 없이 완료했다. 하지만 과거 새 인식과
7페이지의 글자/좌표가 달랐다. 문단 OCR 응답부터 이미 달라진 입력이 원인이었고,
공통 줄 이미지 771개의 응답은 같았다. 새 입력을 고정한 순차 배치/구·신 검증기는 동일했다.
원본 상수 17을 새 문단 OCR이 1로 읽은 사례를 원본 crop으로 확인했다. 따라서 전체 새 인식의
정확도 유지가 입증됐다고 하지 않는다. 원문 인식 안정성도 남은 우선 검증 대상이다.

`tools/profile_ocr_resources.py --out 새폴더 -- python -u ...`로 실행 명령을 감싼다.
`samples.jsonl`에 코어별 CPU, 가용 RAM, 대상 프로세스 트리 RSS/누적 CPU 시간,
호스트 디스크 누적 카운터, GPU 사용률/전력, VLM 실행·대기 요청 수와 로그 시각을 기록한다.
호스트 수치에는 다른 앱 부하가 포함되며 RSS 합에는 공유 메모리 중복이 있을 수 있다.
GPU/VLM 표본의 age_seconds를 확인하고 오래된 표본을 현재값으로 해석하지 않는다.
VLM은 주기마다 한 번의 제한된 읽기 요청만 하며 컨테이너 안에 상주 모니터를 남기지 않는다.

`tools/benchmark_cpu_startup.py`는 완료된 기준 DB를 읽기 전용으로 열고,
원본 해시를 대조한 뒤 새 캐시로 현재 overlay와 기준 PDF를 비교한다.

원시 결과: `tmp/performance-max/baseline-full/`, `baseline-output/`,
`candidate-startup-profile/`, `candidate-startup/`.

아직 전체 성능 최대화가 완료된 것은 아니다. 다음은 남은 검증 대상이다.

1. 기본 PaddleX 서버의 꺼진 `layout_prep_cpu_workers` 옵션 효과와 동작 동일성.
2. 메모리 여유/프로세스 시작을 함께 통제한 반복 비교 및 더 긴 문서의 안정성.
3. 유실 보완의 CPU 후보 탐색 병렬화/탐지 중복 제거 및 아직 순차인 경계 보완의 겹치기.
4. 각 단계 최적화를 합친 실제 전체 실행 및 서로 다른 긴 문서의 안정성/성능 재측정.
5. VM/호스트 메모리 균형과 GPU 메모리 예약. 아직 OS/서버 설정을 변경하지 않았다.
6. 통합 실행에서 드러난 원문 문단 OCR 응답 변동과 숫자/코드 누락의 원인 및 방지책.

추가 진단은 `DOCUMENT_REPEATABILITY.md`를 참고한다. 동일 10페이지 바이트를 순차로
3회 보내도 일부 문자가 달라졌으며 현재 vLLM 요청은 이미 temperature=0이다.
GPU ≤10%인 유효 표본 17개 모두에서 VLM 실행/대기 요청이 없었다. 문단 OCR에서는
서버의 VLM 전 준비 단계를 먼저 분리 측정해야 하며, line-ocr 전체의 원인으로 일반화하지 않는다.

서버 CPU 분리 측정은 `SERVER_PREPARATION.md`에 정리했다. 10페이지 이미지 변환 5.419초에
비해 박스 준비와 JPEG 생성은 짧았다. 독립 PDFium 4프로세스 + 공유 메모리 실험은
풀 재사용 시 순차 4.794초 → 2.939초(변환만 약 38.7%)였고 모든 픽셀이 같았다.
첫 풀 시작은 더 느렸다. 아직 운영 연결 전 후보이며, 다른 PDF를 지원하는 풀 재사용,
메모리/시간 초과/오류 복구와 전체 처리 비교가 필요하다. 운영 설정은 그대로다.

후속 `SERVER_PDF_POOL.md` 단계에서 운영 API 연결을 적용했다. PDF 작업자 4개 재사용,
별도 예약 예산 8192MiB, 순차 복구 및 이미지 보완 단계에서 풀 회수를 포함한다.
기존 클라이언트 CPU 상한 16개/16384MiB와 GPU 모델·옵션·캐시 키는 유지했다.
실제/폼/회전 표본 반복 173페이지 처리의 픽셀·PDFInfo가 같았고, 전체 회귀 196개와
추가 풀 반환을 포함한 서버 모듈 회귀 13개가 통과했다.

새 32페이지 전체 OCR은 165.802초에 완료됐다. 화면 픽셀 변화는 없지만 이전 새 인식과
4페이지의 글자/좌표가 달랐다. 보완 전 문단 문자열부터 차이가 있었고 공통 줄 응답 771개는
같았다. 전체 OCR 정답률 또는 GPU 100% 유지가 입증된 것은 아니며 목표는 계속 진행 중이다.
원시 자료/복구 방법은 위 문서를 참고한다. 위 "운영 연결 전"은 앞선 실험 시점의 기록이다.

### WSL 재시작 후: 긴 획 탐지 CPU/메모리 최적화

사용자 요청으로 Docker Desktop 정상 종료 → WSL shutdown → Docker 시작을 수행했다.
기존 OCR 작업이 없는 것을 먼저 확인했고 서비스 3개 healthy, RTX 5080 재인식,
기존 별도 bash 컨테이너도 원래 실행 상태로 복원했다. 데이터·모델은 삭제하지 않았다.

`ocr_render._long_runs`의 전체 크기 int32 배열을 행 chunk/Boolean 구간 계산으로 대체했다.
고정된 실제 32페이지 보완 준비 A/B 4회: 중앙값 59.351 → 35.868초(약 39.6% 단축).
405개 탐지·9개 PNG·텍스트/판정/체크포인트 모두 동일했다. 적용 후 CPU 풀을 통한
전 페이지 overlay도 원시 PNG 응답만 재사용해 탐지를 다시 계산했고, 기존 최종 PDF의
글자·좌표·픽셀·품질 판정이 같았다. 실제 작업자 9개/상한 16개, 32페이지, 복구 0회.

복구 스냅샷과 상세 근거는 `RULE_RUN_OPTIMIZATION.md`를 참고한다. 모델/해상도/임계값은
그대로다. 이 결과는 CPU 준비 단계의 개선이며 GPU 100% 유지 또는 전체 새 인식의
정확도 증명을 뜻하지 않는다. 통합 새 OCR 반복과 더 다양한 문서 안정성 검증은 남아 있다.

적용 후 전체 오프라인 회귀 203개(154.361초), 파일 76개/구현 모듈 23개 구조 검사 통과.

### 전체 재측정: 다른 앱과 GPU 경합 분리

`GPU_CONTENTION.md`에 기록했다. 새 전체 OCR이 324.925초로 느려졌지만 본문 GPU 평균은
90.9%였다. 프로세스별 동일 엔진 표본에서 Chrome 78%, WSL VM 16%가 관측됐고 사용자가
Chrome GPU 작업을 수행 중임을 확인했다. 사용자가 직접 부하를 낮춘 뒤 설정 변경 없이
10페이지 반복 중앙값 21.393 → 12.622초, 32페이지 전체 173.629초가 관측됐다.
워밍업/메모리/모델 응답을 모두 통제한 교차 실험은 아니므로 일반적인 개선 보장은 아니다.

Windows 프로세스별 GPU 엔진 기록을 선택 옵션 `--windows-gpu`로 추가했다.
GPU 전체 수치를 OCR에 귀속하거나 서로 다른 엔진의 수치를 합산하지 않는다.
VRAM 예약값은 0.8 그대로이며 모델/입력/임계값과 다른 사용자 앱은 변경하지 않았다.
새 분석 도구의 회귀 5개 및 파일 80개/모듈 23개 구조 검사를 통과했다.

현재 낮은 부하 표본의 유실 보완은 41.66초이며 GPU 저사용 표본 7개 모두 VLM 작업이 없었다.
다음은 이 순차 CPU 탐색/준비의 함수별 측정과 제한된 병렬화 검증이다. 전체 목표는 미완료다.
새 인식의 기존 문자열 변동은 남지만, 공통 줄 이미지 응답 771개와 화면 픽셀은 같다.

### 보완 CPU 풀의 분리 실험 완료 (운영 연결 전)

`REPAIR_CPU_POOL_EXPERIMENT.md`를 참고한다. cProfile에서 29.008초 중 탐지 26.089초,
display-list 렌더링 18.259초(중첩 누적 시간)를 확인했다. 페이지별 독립 PDF 프로세스가
좌표만 준비하는 제한된 실험 경로를 만들었다. 원래 부모가 PNG/HTTP/판정/체크포인트를 처리한다.

기록 OCR을 고정한 32페이지 교차 비교: 순차 중앙값 29.018초 → 4개 9.607초,
8개 요청/실제 5개 8.716초. 8회 모두 405개 탐지·9개 PNG·판정/체크포인트가 같았다.
실제 GPU 보완 인식까지 같은 HTTP 겹치기로 교차 비교하면 34.861초 → 23.372초(약 33%)였고
4회 모두 같은 결과였다. 이 단계의 개선이며 전체 OCR 시간이나 정답률 보장은 아니다.

이 분리 실험 시점에는 운영 코드를 바꾸지 않았다. 실험의 실패 방식은 중단이므로, 운영 연결에는 순차 복구,
재개/중단/체크포인트 실패의 처리와 더 긴 문서/최종 PDF 검증이 필요하다. 풀 회귀 6개와
파일 82개/모듈 23개 구조 검사를 통과했다. 모델·서버·운영 캐시는 그대로 보존했다.

### 보완 CPU 풀 운영 연결

`REPAIR_CPU_PREPARATION.md`에 구현·제한·복구 방법을 기록했다. `--cpu-workers` 상한 안에서
이 단계는 최대 4개를 사용하며 원본 탐지 좌표만 준비한다. 완료된 재개 항목은 건너뛰고,
풀 오류·사망·시간 초과·메모리 압박은 현재 블록부터 순차 복구한다. 기존 OCR/중간 저장을
반복하지 않으며 체크포인트 쓰기 실패와 사용자 중단은 숨기지 않는다.

운영 경로의 기록 응답 고정 32페이지 교차 비교는 순차 34.313초 → 실제 4개 9.675초였다.
405개 탐지·9개 PNG·텍스트/판정/체크포인트가 네 번 모두 같았고 복구는 없었다.
복구/재개/회전/crop/주석/실제 작업자 사망/40페이지 교체 회귀 9개가 통과했다.
이 결과는 보완 CPU 준비 단계이며 새 모델 정답률·전체 OCR 속도·GPU 100% 유지의 보장이 아니다.

후속 전체 회귀 223개(177.155초)와 파일 84개/모듈 24개 구조 검사 통과.
새 32페이지 전체 OCR도 180.568초에 완료됐다. 시작 메모리에 맞춰 보완 실제 2개,
overlay 5개, 검증 8개가 사용됐고 모두 복구 0회였다. 보완 구간은 직전 약 41.66초에서
약 29.63초로 줄었지만 본문/overlay가 늘어 **전체는 직전 173.629초보다 느렸다**.
전체 개선으로 일반화하지 않으며 메모리/워밍업 조건을 통제한 반복이 남아 있다.

최종 픽셀/페이지 findings는 같았지만 세 페이지(3·11·15)의 글자/좌표와 line decisions가
달라 엄격한 비교는 실패로 기록했다. 세 페이지는 보완 전 본문 문자열부터 달랐고 박스와
공통 줄 이미지 응답 771개는 같았다. 고정 입력 CPU 동일성과 새 인식 정답률을 구분한다.
Chrome 3D 최고 3%, WSL VM 최고 93%로 이전 큰 경합은 관측되지 않았고, VRAM 잔여량과
공유 GPU 메모리 사용은 추가 점검 대상이다. VRAM 0.8/서버/OS 설정은 변경하지 않았다.

### VRAM 예약 0.8/0.6 교차 실험 — 반영 보류, 0.8 복구

`VRAM_RESERVATION_EXPERIMENT.md`에 A1→B1→A2→B2의 12회 같은 입력 반복과
세 차례 전체 OCR, 원문 대조를 기록했다. 유사 순서의 전체 시간은 0.8 103.906초,
0.6 99.544/99.014초였지만 이전 180.568초와의 큰 차이에는 재시작/상태 영향이 있었다.
0.6의 메모리 절약 관측도 두 번에 걸쳐 동일하게 재현되지는 않았다.

원본 이미지에서 확인한 "덱"을 0.6 후보가 6회 중 2회 "텍"으로 인식했다. 0.8의
해당 6회에는 없었다. 인과/전체 정답률을 단정하지 않되 정확도 유지가 입증되지 않아
후보를 기본 반영하지 않았고, 설정 파일/런타임 0.8과 healthy를 확인했다.
기존 CPU 최적화·모델·캐시·출력물은 보존했다. VLM만 유휴 상태에서 재시작했다.

성능 비교 도구에 요청 해시/좌표에 묶인 원문 대조 게이트를 남겼고 새 회귀 6개와
파일 86개/모듈 24개 구조 검사 통과. 다음 최적화는 변경 없는 입력/출력을 검증할 수 있는
CPU 경계 준비와 장기 실행 메모리 상태다. 전체 성능 목표는 아직 완료하지 않았다.

### 경계 준비/HTTP 겹치기 — 입력·출력 보존

`BOUNDARY_PREFETCH.md`에 경계 단계 측정과 저장 순서/복구를 정리했다. 32페이지에서
CPU 준비는 약 3초로 별도 프로세스 풀의 기대 이득이 작았다. 단일 HTTP 실행 중 다음
블록/페이지의 CPU 준비만 겹치도록 했고, CLI 기본 연결 및 `--no-prefetch` 복구를 남겼다.
원본·모델·zoom·임계값·GPU 요청 동시성 1·경계 캐시 버전은 그대로다.

단독 교차 비교 두 묶음은 단계 중앙값 24.847 → 24.094초, 25.650 → 24.447초였다.
두 번째 묶음에서 HTTP 바깥 시간은 2.965 → 1.170초로 줄었다. 이는 전체 책 속도가
아닌 경계 단계의 소폭 개선이며 GPU 100% 유지나 외부 GPU 부하 완전 제거를 뜻하지 않는다.
기록된 고정 응답 4회와 실제 응답 12회 모두 PNG 26개/전체 레이아웃/감사/체크포인트가
기준과 동일했다. 최초 실제 4회는 회귀 테스트와 경쟁했으므로 속도 비교에서는 제외한다.

새 `boundary_feed_stats`는 검증 보고서의 추가 진단 필드다. 페이지 저장은 계속 소유
스레드에서 하고, 실패 페이지는 완료 처리하지 않으며 다음 요청 전에 앞 페이지를 저장한다.
진행 중인 사용자 OCR은 재시작하지 않았고 기존 결과/캐시/HPS 설정도 변경하지 않았다.
다음 남은 범위는 전체 실행에서의 개선 폭과 서버 요청 내부 CPU/GPU 공백, 장기 메모리 상태다.

이 단계의 최종 전체 오프라인 회귀 239개(168.510초), 파일 88개/구현 모듈 24개
구조 검사와 공백 검사가 통과했다. CLI 기본 및 `--no-prefetch` 복구도 검증했다.

같은 경계 레이아웃의 후속 32페이지 overlay를 원시 PNG 응답 키 771개만 재사용하여
다시 만들었다(새 HTTP 0회). 전 페이지 픽셀/글자/좌표/페이지 판정/줄 판정이 기준과 같다.
기존 미배정 상자 경고 48개는 남아 있다. 결과는 `boundary-prefetch-pdf-check/`에 보관했다.

### 문자 보존과 비교 CPU 비용 개선

후속 요청에서 HTML/표 안 코드 유실과 숫자/주소 순서 검사 누락을 수정하고,
동일 문자열 비교 및 이메일 없는 문단의 정규식 비용을 줄였다. 세부 변경은
`TEXT_PRESERVATION_PERFORMANCE.md`를 참고한다. 기존 CPU/GPU 설정은 유지했다.
기록 133블록의 비교 단계 중앙값은 43.04→29.23ms이며 전체 OCR 단축률이 아니다.
실제 32페이지 오프라인 재생의 글자·좌표·픽셀·페이지/줄 판정은 기준과 정확히 같았다.
전체 회귀 247개와 추가 표 좌표 검사(최종 문자 회귀 9개)가 통과했다.
모델의 새 인식 변동이나 전체 책의 정답률 개선을 검증한 것은 아니다.
