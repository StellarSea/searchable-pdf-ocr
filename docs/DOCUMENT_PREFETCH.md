# 본문 OCR 요청 겹치기

CLI는 기본적으로 `--ocr-requests 2`로 본문 OCR HTTP 요청을 최대 2개까지 진행한다.
첫 묶음을 요청한 뒤, 원래 PDF 소유 스레드가 다음 묶음을 준비해 전송한다.
응답 순서와 무관하게 원래 페이지 순서로 검증·체크포인트 저장을 수행한다.
GPU 모델 작업자를 추가하거나 문서 인식 설정을 변경하는 기능이 아니다.

## 제한과 복구

- 기존 `--batch` 경계(기본 10페이지), 원본 입력, 렌더링 배율, API 옵션을 유지한다.
- 미소비 요청/응답은 최대 2묶음이다. PDF/SQLite 객체는 HTTP 스레드에 전달하지 않는다.
- 전송 예산은 입력 바이트의 4배로 추정해 256 MiB 안에서 동시 요청을 허용한다.
  한 묶음만으로 예산을 넘으면 축소/재분할하지 않고 단독 처리한다. 이는 동시 요청
  입장 제한이며 PDF 준비, 서버 디코딩 이미지, 응답 등을 포함한 전체 RAM 상한은 아니다.
- 요청 오류가 나면 추가 병렬 공급을 끄고, 이미 보낸 HTTP 요청을 기다린 뒤 실패한 묶음을
  한 번 순차 재시도한다. 기존 전송 계층의 제한된 재시도와 별개다. 400/401 등 영구 HTTP
  오류와 응답 페이지 수/형식 오류는 재시도하지 않는다. 서비스를 재시작하지 않는다.
- 계속 실패하면 연속으로 검증·저장된 페이지까지만 재개 지점으로 남긴다. 뒤쪽 묶음의
  성공 응답을 앞쪽 실패 페이지 대신 저장하지 않는다. 다음 실행에서 미저장 묶음은 다시 인식한다.
- 중단 시 미시작 요청은 취소하고, 시작된 HTTP 요청은 정리될 때까지 기다린다.
  이미 서버에 도착한 추론을 강제로 취소할 수는 없다.
- `--ocr-requests 1`은 기존 순차 요청으로 복구한다. `--batch 0` 전체 전송에는 겹침을 적용하지 않는다.
  기존 `--no-prefetch`/`--no-gpu-prefetch`는 줄 OCR 옵션이므로 이 기능과 별개다.
- 캐시/완료 식별자와 보조 파일 형식은 변경하지 않는다. 라이브러리 `run_ocr()` 기본값은
  호환성을 위해 `document_requests=1`이며 CLI가 2를 전달한다.

## 현재 서버에서 기대할 수 있는 효과

2026-09-13 설치된 PaddleX 서버를 읽기 전용으로 확인했다. `PipelineWrapper`는 기본
`PADDLE_PDX_SERVING_SERIAL_PIPELINE_CALLS=True`에서 예측기 호출을 직렬화하며, 해당 환경 변수의
별도 설정은 없었다. 요청 이미지 준비는 예측 호출 전, 응답 후처리는 호출 후에 수행한다.
따라서 클라이언트 분할·전송과 서버의 입력 준비/응답 후처리를 다음 요청과 겹칠 수 있지만,
두 예측기를 동시에 돌리거나 예측기 내부의 모든 GPU 공백을 제거하는 것은 아니다.
이 안전 직렬화 설정을 해제하지 않았다. GPU 사용률 100%나 속도 향상률은 보장하지 않는다.

## 검증

`tests/test_document_prefetch.py`는 실제 작은 PDF의 분할 입력 해시·문자 좌표·픽셀 보존,
동시 요청/역순 완료/2묶음 상한, 메모리 입장 제한, 순차 복구, 영구 오류, SQLite 재개,
완료 캐시, 전체 전송, 종료 시 정리를 오프라인으로 검사한다. OCR 응답은 가짜 서버 콜백으로
통제한다. 이 검사는 스케줄링과 데이터 보존 검증이며 실제 모델 인식 정확도 측정은 아니다.
진행 중인 OCR에 간섭하지 않도록 이 변경의 실제 GPU 속도/인식 A/B 실험은 실행하지 않았다.

2026-09-13 전체 회귀 148개를 통과했다. 이후 오류·전체 전송 등 테스트 4개를 추가한 최종
상태에서 본문 선행 공급 12개와 자동 실행 통합 25개를 다시 통과했다. 정적 구조 검사도 통과했다.

다음 실행부터 기존 명령 그대로 적용된다. `[ocr-feed]` 완료 요약에서 요청 수,
최대 미소비 요청 수, 준비/대기 시간, 순차 복구 횟수를 확인할 수 있다.
