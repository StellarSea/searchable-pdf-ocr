# PDF 변환의 공유 메모리 창 제한

## 실행 중 관측과 적용 상태

2026-09-14 `신호 및 시스템.pdf` OCR이 실행 중인 상태에서 읽기 전용으로 확인했다.
호스트 RAM 가용량은 첫 표본에서 약 4.9GiB였고 이후 약 8~10GiB로 변했다.
Docker VM 총 RAM은 약 31.2GiB이며, API/VLM/줄 서버가 같은 VM 메모리를 사용한다.

서버 로그의 10페이지 PDF 준비는 `workers=4`여도 `parallel=False`인 요청이 많았다.
기존 예약량 약 7.84~7.94GB와 2GiB 여유 조건을 만족하지 못하는 구간이 있었다.
관측된 순차 변환은 약 5.4~6.9초, 병렬 변환 두 구간은 약 4.2초였다. 입력/부하가
통제된 교차 측정이 아니므로 그 차이를 이번 개선의 효과로 주장하지 않는다.

**코드는 수정했고 회귀/호스트 PDFium 표본 검증을 마쳤으나 운영 서버에는 아직
반영하지 않았다.** 사용자 OCR 프로세스 PID 31140이 계속 실행 중이므로 API나
WSL/Docker를 재시작하지 않았다. 현재 작업 속도가 이 코드로 빨라졌다는 뜻은 아니다.

## 변경

기존 구현은 한 요청의 모든 페이지에 공유 출력 버퍼를 먼저 할당하고 모든 작업이
끝난 뒤 최종 NumPy 배열로 복사했다. 새 구현은 동시에 진행하는 페이지 수만큼만
공유 출력 버퍼를 유지한다. 완료한 작업은 원래 페이지 위치에 복사한 뒤 공유 메모리를
해제하며, 그 다음 페이지를 제출한다. 먼저 완료된 뒷페이지가 앞페이지를 기다리며
공유 버퍼를 붙잡지 않아도 최종 반환 순서는 원래 페이지 순서다.

입장 시 최대 4페이지부터 최소 2페이지까지 활성 창을 줄여 메모리·공유 공간 여유를
확인한다. 기존 작업자 풀의 전체 인터프리터 비용은 활성 창이 줄어도 모두 예약한다.
예약량에는 최종 전체 배열, 활성 공유 출력, 작업자 렌더 버퍼, 입력 bytes 복사,
인터프리터 및 기존 256MiB 여유를 포함한다. 기존 2GiB 시스템 여유와 8192MiB
설정 예산은 유지한다. 작은 요청이나 최소 창도 예산을 넘는 요청은 계속 순차 처리한다.

`[pdf-cpu]`에는 `window_pages`, `peak_pending_pages`, `available_memory_bytes`,
`available_shared_bytes`, `admission_reason`을 추가했다. 이 필드는 진단용이다.
모델 입력 이미지/크기/해상도/페이지 순서, 원시 캐시 키, HTTP 형식은 변경하지 않는다.
작업자 오류/사망/시간 초과/중단에서는 풀을 먼저 회수한 뒤 남은 공유 메모리를
해제한다. 일부 페이지가 복사됐더라도 부분 결과를 반환하지 않고 전체 순차 복구한다.

## 확인 결과와 한계

서버 관련 오프라인 검사 **20개 통과(7.216초)**. 70페이지 처리 중 작업자 재생성,
완료 순서가 뒤바뀐 페이지, 활성 창 2/풀 4, 메모리 입장, 뒤쪽 창 실패, 작업자 사망,
시간 초과, 부분 제출 실패와 공유 메모리 회수를 포함한다. 구문/의존성 검사도
Python 파일 91개/구현 모듈 24개를 통과했다. 전체 회귀는 이번 실행 중 OCR과의
자원 경합을 피하기 위해 반복하지 않았다.

Windows 호스트 PDFium을 동일한 렌더 콜백으로 주입해 기존 코드와 비교했다.
실제 진단 PDF 4페이지와 회전/crop/폼/주석 fixture 6페이지를 각각 두 번 교차 실행했다.
총 40페이지 처리의 이미지 크기·픽셀 SHA·순서·메타데이터가 전부 같았고, 모든
반환 배열은 자체 메모리를 소유했다. 모델·HTTP 호출은 없다. 이 테스트는 서버의
PaddleX/PDFInfo 구현 자체나 새 문단 OCR 정확도를 검증하는 테스트는 아니다.
기존 기본 렌더 콜백과 PDFInfo 생성 코드는 변경하지 않았다.

| 입력 / 작업자 2개 | 기존 공유 메모리 최고값 | 새 공유 메모리 최고값 |
|---|---:|---:|
| 실제 4페이지 | 928,527,786 bytes | 466,416,294 bytes |
| 회전·폼 등 6페이지 | 99,824,221 bytes | 33,699,389 bytes |

실제 4페이지 변환 중앙값은 2.183→1.916초였다. 실행 중 OCR과 자원을 공유했으므로
**약 12%라는 값을 운영 속도 향상률로 사용하지 않는다.** 첫 6페이지 시도는 메모리
입장을 통과하지 못해 벤치마크가 중단됐으며 성공 수치에 포함하지 않았다.

현재 책의 첫 10페이지를 이미지로 디코딩하지 않고 크기/입력 bytes만 확인하여
가용 메모리 8GiB의 입장 결정을 비교했다. 실제 풀을 만들거나 VM 설정을 바꾸지 않았다.

| 방식 | 예약 메모리 | 공유 메모리 예약 | 병렬 입장 |
|---|---:|---:|---|
| 기존 | 7,919,239,242 bytes | 2,524,931,461 bytes | 불가 |
| 새 구현 | 6,085,916,409 bytes | 791,857,237 bytes | 활성 3페이지 / 풀 4개 |

약 23% 낮은 예약량으로 기존보다 메모리 부족 시 병렬화를 유지할 여지가 생긴다.
전체 OCR 처리시간의 개선 폭은 유휴 상태에서 운영 반영 후 동일 입력으로 측정해야 한다.
실행 중 사용자의 작업을 중단하거나 서비스에 새 진단 OCR을 보내지는 않았다.

## 반영과 재현

코드가 읽기 전용 bind mount되어 있으므로 **모든 OCR 작업이 끝난 뒤** API 서비스만
재시작하면 다음 작업부터 적용된다. 진행 중에는 실행하지 않는다.

```powershell
docker compose -f C:\ocr\compose\compose.yaml restart paddleocr-vl-api
python -m unittest discover -s tests -p 'test_server*.py' -v
python tools/check_architecture.py
```

반영 뒤 `[pdf-cpu]`의 `window_pages`/`admission_reason`으로 새 경로를 확인한다.
원시 자료와 변경 전 코드: `tmp/pdf-window-improvement/`.
`comparison.json`은 실제 픽셀 비교, `admission-final.json`은 가용 메모리를 고정한
입장 계산이다. `benchmark.py`는 호스트 PDFium 콜백을 주입한 한정된 재현 스크립트다.
