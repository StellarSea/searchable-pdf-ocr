# 적용된 서버 PDF 변환 풀

2026-09-14. 기본 PaddleX API의 PDF→이미지 변환만 병렬화했다. HPS를 재도입하지 않았고,
같은 Docker 이미지·GPU 모델·해상도·인식 옵션·원시 캐시 키를 유지한다.

## 설정과 소유권

- Compose의 API 서비스만 `ocr_server_entrypoint.py`로 시작한다. 모델 서버와 줄 서버의
  명령/이미지는 이 변경에서 수정하지 않았다.
- `OCR_PDF_WORKERS=4`: 서버 시작 시 준비하고, PDF 묶음 간에 재사용하는 spawn 작업자.
- `OCR_PDF_MEMORY_MB=8192`: 공유 출력/최종 배열/작업자 렌더·인터프리터/입력 버퍼를
  포함한 예약 예산. 실제 가용 메모리에서 2GiB를 남기는 조건과 `/dev/shm` 여유도 검사한다.
  이 값은 컨테이너 전체 메모리 상한이 아니다. 호스트의 기존 `--cpu-memory-mb 16384`는 그대로다.
- `OCR_PDF_TIMEOUT=60`: 작업자 초기화 및 한 번의 페이지 작업 대기에 각각 적용되는 상한(초).
- 한 reader의 PDF 요청은 소유 스레드 잠금으로 직렬 입장한다. 페이지만 작업자별로 병렬 처리한다.
  PDFium 문서·폼은 각 작업자가 독립적으로 열고 닫는다. 부모의 metadata 접근은 원래 PDFium 잠금을 사용한다.
- 문서 입력은 요청별 공유 메모리로 전달한다. 다른 PDF의 내용이나 페이지를 재사용하지 않는다.
- 부모만 공유 메모리를 생성/해제한다. 결과를 일반 NumPy 소유 배열로 복사한 후 해제하므로
  모델/HTTP 코드에는 공유 메모리 수명 관리 책임이 넘어가지 않는다.
- 풀은 작업자당 32페이지 이후 재생성한다. 모델이나 GPU 추론 객체는 작업자에 생성하지 않는다.

이미지(문단 보완 등) 입력으로 넘어가면 PDF 풀을 회수하여 이후 경계 탐지/overlay에 메모리를
돌려준다. 다음 PDF가 오면 다시 생성할 수 있다. 서버 종료 시에도 회수한다.
PDF만 호출하고 아무 입력도 오지 않는 경우 풀은 다음 요청/서버 종료까지 상주한다.

## 복구와 예외

작은 PDF(예약 이미지 합계 64MiB 미만), 한 페이지, 128페이지 초과, 메모리/공유 공간 부족은
기존 순차 reader를 사용한다. 원래 픽셀 제한·예외·max_num_imgs 처리를 유지한다.

초기화/렌더 실패, 잘못된 반환 좌표, 부분 제출 실패, 작업자 사망/시간 초과, 처리 중
메모리 부족은 먼저 해당 풀을 terminate/join하고 공유 메모리를 해제한 뒤 전체 요청을
기존 reader로 다시 처리한다. 부분 결과를 반환하지 않는다. 같은 실패를 반복하지 않도록
해당 서버 생명주기에서 병렬화를 비활성화한다. 원래 reader도 실패하면 원래 오류가 전달된다.
KeyboardInterrupt 등 중단은 풀을 정리하고 그대로 전파한다. 로그 출력 실패는 재인식을 유발하지 않는다.

서비스 로그의 `[pdf-cpu]`에 parallel, 예약량, 시간, 복구 사유를 기록한다.
HTTP 응답·저장물 형식은 바뀌지 않는다.

## 검증

`benchmark_server_pdf.py`에서 같은 풀로 10페이지 실제 표본 → 회전/잘린 페이지/폼/주석을
포함한 6페이지 fixture → 실제 표본 첫 3페이지 → 전체 표본을 바꿔 처리하고 fixture를 24번 반복했다.
합계 **173페이지 처리**이며 별개의 실제 173페이지 표본이라는 뜻은 아니다.

- 모든 이미지 shape/dtype/픽셀 SHA-256 및 PDFInfo가 기존 reader와 일치.
- 전체 10페이지 변환: 순차 5.468초, 병렬 3.188 / 3.207초. 준비만 측정한 값이다.
- 준비된 풀 생성 1.994초는 별도 기록. 반복 중 작업자 재생성 구간도 통과했다.
- 잘못된 입력의 정답을 판단하거나 문단 OCR 자체의 정답률을 평가하는 테스트는 아니다.
- 기본 전체 회귀 196개 통과(168.466초). 이후 추가한 이미지 단계의 풀 반환/재시작 테스트를
  포함한 이 모듈의 13개 회귀도 통과했다. 현재 Python 구조 검사 74파일/23모듈 통과.

원시 결과: `tmp/performance-max/server-reader-verified/comparison.json`.
준비와 전달 방식의 이전 실험은 `SERVER_PREPARATION.md`를 참고한다.

## 실제 API 연결 후 관측

같은 10페이지 bytes를 보낸 적용 전 3회는 16.959 / 13.540 / 12.497초,
적용 후 4회는 12.967 / 12.389 / 11.326 / 9.889초였다.
재시작/워밍업/호스트 부하 및 vLLM 반복 변동이 있으므로 이 차이 전부를 코드 효과로 주장하지 않는다.
네 요청 모두 실제 로그에서 parallel=True/fallback=None을 확인했다.

약 1초 표본에서 GPU 평균은 적용 전 32.45%, 후 23.02%였다. ≤10% 표본은 각각 28/44,
29/47이었다. 요청 반복 횟수/동작 조건이 다르며, GPU 평균 상승이나 저사용 구간 제거는
확인하지 못했다. 성능 평가는 사용률 숫자보다 처리 시간과 결과 보존으로 한다.
전후 모두 원시 문단 OCR에 반복 변동이 있었고, 이를 PDF 변환 오류나 정답률 개선으로 숨기지 않는다.

32페이지 전체 실행에서도 PDF 4묶음이 병렬 처리되었고 문단 단계 37.4초,
이미지 보완으로 전환한 뒤 PDF 작업자 4개 종료와 `/dev/shm` 사용 0을 확인했다.
전체 실행의 최종 결과는 해당 진단의 완료 보고서로 별도 확인한다.

전체 실행은 **165.802초**에 완료(`completed_with_warnings`, `validation_failed=False`)했다.
CPU 준비 실제 5개로 32페이지 전부 처리, 복구 0회. GPU 공급 34요청/631이미지, 오류 0회.
최종 검증은 메모리 예산에 따라 실제 5개 작업자로 32페이지 처리, 순차 복구 0회였다.
이전 전체 실행 217.620초와 입력 PDF는 같지만 호스트 부하와 인식 응답/워밍업이 다르므로
차이 전부를 이번 코드 효과로 보거나 24% 개선을 일반적인 보장 수치로 사용하지 않는다.

이전 완료 PDF와 화면 픽셀 차이는 없었다. 글자/좌표는 표본 p1, p3, p22, p32에서 달랐다.
보완 전 문단 OCR 문자열로 복원해도 p1, p3, p22, p30, p32의 입력이 이미 달랐고,
그 단계의 박스 좌표는 모두 같았다. 공통 줄 이미지 응답 771개도 모두 같았다.
이전 `17→1` 오독 사례는 이번에 `17`로 읽혔지만, 이것을 전처리가 모델의 정확도를
개선했다는 증거로 삼지 않는다. 기존 vLLM 반복 변동과 전체 정답률 검증은 별도 문제다.
따라서 완료 PDF 비교 도구의 엄격한 동일성 판정은 통과로 숨기지 않고 종료 코드 1을 남겼다.

비교: `server-reader-full-comparison.json`, 발생 단계 분리: `server-reader-upstream-analysis.json`.

자료: `server-reader-before[-profile]/`, `server-reader-after[-profile]/`,
`server-reader-full-output/`, `server-reader-full-profile/` (모두 `tmp/performance-max` 아래).

## 운영 옵션과 되돌리기

평소 OCR 명령은 바꾸지 않아도 된다. 변환만 원래 방식으로 되돌릴 때는 OCR 작업이 없는 상태에서:

```powershell
$env:OCR_PDF_WORKERS = '0'
docker compose -f C:\ocr\compose\compose.yaml up -d --no-deps --pull never paddleocr-vl-api
```

지속적으로 해제하려면 `compose/.env`에 같은 값을 지정한다. 다시 켜려면 그 값을 4로 바꾸고
유휴 상태에서 같은 API 서비스만 재생성한다. 원본이나 OCR 결과를 삭제할 필요는 없다.
적용 전 전체 Compose 사본은 `tmp/performance-max/server-reader-rollback/compose.yaml`에 있다.
이 사본은 이후 다른 설정 변경을 덮어쓸 수 있으므로 단순 해제에는 위 환경 변수를 우선 사용한다.

이전 컨테이너의 `/tmp` 진단 사본은 API 재생성으로 제거됐다. 원본 요청/응답과 비교 결과는
호스트의 `tmp/performance-max`에 보관되어 있어 다시 만들 수 있다. 운영 PDF/캐시는 삭제하지 않았다.
