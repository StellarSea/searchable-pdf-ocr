# CPU 페이지 준비 병렬화 실험

아래는 단계별 실험 당시의 기록이다. 이후 운영 기본값 4개에 캐시 우선/예산/순차 복구를 적용했다.
그 뒤 사용자 요청으로 운영 기본 작업자 상한을 8개, 이후 16개로 변경했으며, 아래 과거 측정값은 그대로 보존한다.
현재 동작은 [CPU 준비 사용 안내](CPU_PREPARATION.md)를 기준으로 한다.

2026-09-13, Ryzen 7 9700X(8코어/16논리 프로세서), RAM 약 64 GiB에서 측정했다.
**운영 OCR에는 아직 적용하지 않은 독립 실험**이다. GPU 작업자 수는 바꾸지 않았다.
기존 원본·운영 캐시·출력은 읽기만 했으며, 중단 상태인 OCR을 재실행하지 않았다.

## 결과

`쉽게 배우는 C 자료구조.pdf`의 PDF 기준 6, 7, 29, 38, 66, 147, 166, 188페이지를
각 작업자 수에서 3회 처리했다. 목차·표·여러 문단이 있는 페이지를 포함한다.

| CPU 작업자 | 8페이지 중앙값 | 1개 대비 | 프로세스 트리 최대 RSS 합계 |
|---|---:|---:|---:|
| 1 | 34.395초 | 1.00배 | 1.66 GiB |
| 2 | 19.495초 | 1.76배 | 2.32 GiB |
| 4 | 11.074초 | 3.11배 | 2.63 GiB |
| 8 | 6.886초 | 4.99배 | 3.10 GiB |

이 표본에서는 8개가 가장 빨랐다. 독립 순차 기준 실행은 34.601초였다.
작업자 초기화는 각각 0.958 / 0.939 / 0.981 / 1.506초로 위 처리 시간에서 제외했다.
측정 중 시스템 가용 메모리 최저치는 약 17.6 GiB였다.

### 측정 범위와 한계

- 포함: 운영 `_block_layout`의 줄/표 탐지·문자 분할, 동일 해상도 RGB PNG 준비,
  **실제 PNG 바이트의 프로세스 간 전송**, 부모의 해시 검사·입력 순서 복원.
- 제외: 원본 SHA 계산, 경계 복구, GPU/HTTP OCR, SQLite 캐시, PDF 텍스트 삽입·저장·최종 검증.
- 탐지/응답 캐시 없이 측정했다. 캐시가 따뜻한 실제 재실행에서는 이 개선 효과가 작아질 수 있다.
- 작업자 1→2→4→8 순서로 측정했다. OS 파일 캐시는 통제하지 않았고,
  모든 실행에서 페이지 처리 후 MuPDF 이미지 저장소를 비웠다. 이 저장소 정책은
  운영 코드의 장기 실행 정책과 다르므로 전체 OCR 시간으로 환산하지 않는다.
- 모든 병렬 작업자는 Windows의 보통 이하 우선순위를 사용한다.
- RSS는 50ms 간격의 부모+자식 합계다. 공유 메모리를 중복 계산할 수 있으며 순간 최고치를 놓칠 수 있다.
  작업 전체가 항상 3.1 GiB 이하라는 보장은 아니다.
- 작은 표본이며, 실제 GPU·PDF 쓰기와 동시 실행할 때의 CPU/메모리 경쟁은 아직 측정하지 않았다.

## 정확도 보존 검사

독립 순차 기준과 모든 12회 병렬 결과의 다음 항목이 일치했다.

- 페이지·블록·줄 순서, 줄 좌표와 문자 분할 결과
- OCR로 보낼 PNG의 SHA-256(부모가 실제 수신한 바이트에서 계산)
- 원본에 묶인 crop 키와 PNG 기반 OCR 이미지 키

모델·해상도·임계값을 낮추지 않았다. GPU 인식 결과나 최종 PDF를 생성한 시험은 아니므로
전체 책의 정확도·최종 PDF 좌표 검증을 대신하지 않는다.

`test_cpu_worker_benchmark.py`는 별도 프로세스가 각자 PDF를 여는지 전제로 실제 spawn 실행을
검사하고, 비정렬 입력의 순서 보존·바이트/좌표/키 일치·원본 불변·PNG 예산 초과 시 실패를 검증한다.
추가 후 전체 오프라인 회귀 테스트 107개가 53.554초에 통과했고, 문법·미정의 전역·순환 의존성 검사도 통과했다.

## 구현과 재현

```powershell
python -m pip install -r requirements-dev.txt
python tools/benchmark_cpu_workers.py "input/쉽게 배우는 C 자료구조.pdf" "input/ocr_output/.ocr/쉽게 배우는 C 자료구조_boundary_cache.json" --out tmp/cpu_workers/recheck
```

새 출력 디렉터리를 지정해야 한다. 이번 원시 결과는
`tmp/cpu_workers/primary/comparison.json`, 비교 기준은 같은 폴더의 `reference.json`이다.
`--pages`, `--workers 1 2 4 8`, `--rounds 3`, `--font`로 표본/환경을 명시할 수 있다.
메모리 추정을 위해 작업자 목록은 1부터 시작하며 최대 8까지 허용한다.

작업자는 각자 PDF/폰트를 열며 PyMuPDF 객체를 스레드 사이에서 공유하지 않는다.
대기 작업 수를 작업자 수 이하로 제한하고, 페이지당 보관 PNG 예산 64 MiB를 넘으면
축소하지 않고 실험을 실패시킨다. 1개 작업자의 측정 RSS에 여유를 더한 사전 추정으로
가용 메모리 4 GiB를 남기지 못할 작업자 수는 건너뛴다. 이는 하드 메모리 제한이 아니다.

운영 적용의 다음 검증은 4/8개 페이지 준비 프로세스와 기존 단일 소유자 PDF/SQLite 쓰기,
HTTP/GPU 작업을 연결해 전체 overlay 처리량을 비교하는 것이다. 메모리 제한·순서 보존·실패 시
순차 폴백·따뜻한 캐시 우회와 최종 PDF 픽셀/글자 좌표 동일성도 함께 확인해야 한다.
이 도구를 추가했다고 기존 명령이 자동으로 CPU 8개 작업자를 사용하는 것은 아니다.

## 후속: 실제 GPU + overlay 통합 테스트

같은 날 `benchmark_cpu_overlay.py`로 위 8페이지를 **실제 GPU 줄 OCR, PDF 삽입/저장,
운영 최종 검증까지** 실행했다. 기준은 기존 HTTP 선행 준비가 켜진 기본 overlay다.
작업자 4/8개는 실험용 `prepared_pages` 콜백으로만 연결했다. CLI에는 적용하지 않았다.

세 라운드 순서를 기존→4→8, 4→8→기존, 8→기존→4로 바꾸었고, 매 실행은 새 진단 캐시를 사용했다.
GPU는 기존 설정(작업자 1, 배치 32, 입력 폭 320)을 유지했다.

| 방식 | overlay+저장 중앙값 | 최종 검증 포함 중앙값 | 3회 중 최대 호스트 RSS 합계 |
|---|---:|---:|---:|
| 기존 방식 | 37.900초 | 41.421초 | 1.82 GiB |
| CPU 작업자 4개 | 17.714초 | 21.219초 | 3.07 GiB |
| CPU 작업자 8개 | 18.118초 | 21.614초 | 3.53 GiB |

4개는 overlay/저장 약 53.3%, 검증 포함 약 48.8% 시간을 줄였다.
8개는 4개보다 빨라지지 않았다. 작은 차이로 절대적인 우열을 단정할 수는 없지만,
이 표본에서는 메모리도 덜 쓰는 **4개가 운영 적용 후보로 더 적합**하다.
CPU 준비만 측정했을 때의 5배를 전체 파이프라인에 적용하면 안 된다는 점도 확인했다.

각 실행에서 59개 문단 요청으로 293개 줄 이미지를 실제 GPU에 보냈다. 삽입된 줄은 382개이며,
문단 대체/삽입 실패는 0이었다. 모든 9회에서 OCR 후보·이미지 키·배치 결정·문자 좌표·렌더 픽셀·
품질 보고서가 동일했고 운영 최종 검증도 통과했다. 병렬 준비 실패/순차 폴백은 실제 측정에서는 0회였다.
기존 29페이지의 미배정 박스 5개와 기타 검토 경고는 그대로다. 정확도가 올라갔다는 결과는 아니다.

매 실행 뒤 캐시를 다시 열고 **실험 풀을 명시적으로 우회**해 재실행했다.
9회 모두 HTTP 호출 없이 같은 출력이 나왔으며 overlay/저장 중앙값은 약 2.43~2.44초였다.
아직 캐시 상태를 보고 자동으로 풀을 우회하는 운영 스케줄러를 구현한 것은 아니다.

### 측정 해석

- 위 시간에는 프로세스 시작·종료, 실제 PNG 전송, GPU/HTTP OCR, PDF 삽입/저장이 포함된다.
  운영 `verify` 시간은 별도 기록하고 합계에 더했다. 추가적인 기준 PDF와의 동일성 비교 시간은 제외했다.
- 원본 부분 추출·SHA 계산·문단 OCR·경계 복구는 제외했다. 전체 책 완료 시간을 직접 예측하지 않는다.
- 소스는 동일한 부분 PDF로 고정했고, OS 파일 캐시는 통제하지 않았다. 작업자별 결과를 입력 순서로 소비했다.
- 호스트 RSS는 부모+CPU 자식 프로세스 합계이며 공유 메모리가 중복 집계될 수 있다.
  Docker/GPU 서비스 메모리는 포함하지 않는다. 피크는 문서 내용과 동시 작업에 따라 달라진다.
- 모든 PDF를 원본과 픽셀 비교하고 기준 출력과 글자 좌표 비교했다. PDF 스킬의 시각 검증 절차에 따라
  마지막 4개 작업자 결과의 목차 6/7페이지와 표가 있는 29페이지를 Poppler로 렌더링해 확인했다.
  이는 원본 화면 보존 확인이며, 숨은 텍스트 레이어의 절대적인 정확도 보장은 아니다.

### 재현 및 운영 경계

```powershell
python tools/benchmark_cpu_overlay.py "input/쉽게 배우는 C 자료구조.pdf" "input/ocr_output/.ocr/쉽게 배우는 C 자료구조_boundary_cache.json" --out tmp/cpu_workers/overlay-recheck
```

실제 서버가 `http://127.0.0.1:8081/health`에서 이미 정상 응답해야 한다. 이 도구는 서비스를
시작하거나 재시작하지 않는다. 실험 시작 시 가용 메모리 8 GiB 이상을 요구하지만 하드 메모리 상한은 아니다.
원시 결과는 `tmp/cpu_workers/overlay/comparison.json`, 각 실행의 PDF/캐시/품질 보고서는 하위 폴더에 있다.

작업자가 수집한 탐지 결과는 부모만 SQLite에 저장하고, 글자 삽입·줄 인식 판단도 기존 부모 경로를 사용한다.
큐는 작업자 수 이하, 현재 페이지는 별도로 유지한다. 페이지 준비 오류는 기존 순차 경로로 돌아가며,
호출자가 실패해도 풀을 종료한다. 페이지 수가 작업자 수보다 적으면 시작 장벽도 함께 줄인다.
`test_cpu_worker_benchmark.py`에 실제 프로세스+overlay 동일성, 캐시 재사용, 작업자 실패 폴백,
짧은 표본/호출자 예외 종료 회귀 검사를 추가했다.
최종 전체 오프라인 테스트는 **110개, 56.662초, 모두 통과**했다.
구조 검사도 Python 43개 파일과 구현 모듈 14개의 미정의 전역/순환 의존성 없이 통과했다.

운영에 적용하려면 캐시를 고려한 작업 선택, 전체 메모리 예산, 더 긴 표본에서의 지속 처리량 검증이 필요하다.
**기존 명령의 기본 CPU 작업자 수는 변경하지 않았다.**
