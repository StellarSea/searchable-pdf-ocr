# 경계 보완 HTTP/CPU 겹치기

잘린 상자 보완(`ocr_boundary.repair`)에서 HTTP 요청 하나가 실행되는 동안
소유 스레드가 다음 블록/페이지의 경계 탐지와 PNG를 준비한다.
라이브러리는 `prefetch=False`가 기본이고 운영 CLI는 기본 활성화한다.
기존 `--no-prefetch`로 경계 보완·유실 보완·line-ocr의 해당 겹치기를 해제한다.

## 보존 규칙

- GPU 동시 요청은 이 단계에서 하나다. 다음 요청을 보내기 전 이전 결과를 회수한다.
- PDF 렌더링·배열 분석·문자 보존 판정·SQLite/JSON 저장은 소유 스레드에서 수행한다.
  HTTP 작업자에는 PNG 바이트만 전달한다. PyMuPDF 객체를 스레드 간 공유하지 않는다.
- 페이지 마지막 요청은 다음 페이지 CPU 준비와 겹칠 수 있다. 이전 페이지 응답을
  적용하고 그 페이지 체크포인트 저장에 성공해야 다음 요청을 전송한다.
- 요청 없는 페이지도 앞선 페이지보다 먼저 저장하지 않는다. 캐시 적중 페이지는
  렌더링이나 HTTP 요청 없이 그대로 재사용한다.
- 뒤 페이지 준비에 실패해도 앞선 완료 페이지의 응답과 체크포인트를 먼저 회수한다.
  같은 페이지의 일부 블록만 처리하다 실패하면 그 페이지를 완료 저장하지 않는다.
- HTTP 실패는 기존처럼 예외로 전파한다. 체크포인트 실패/사용자 중단을 재시도로
  삼키지 않는다. 새 요청을 보내기 전에 발생한 저장 실패는 반복 저장하지 않는다.
- 원본 PDF, 원시 OCR 캐시, 모델·정밀도·입력 크기·zoom·임계값·캐시 버전
  `boundary-ink-v3`, 기존 파생 데이터 스키마는 바꾸지 않는다.
- 완료/실패 검증 보고서에는 추가 진단 필드 `boundary_feed_stats`를 남긴다.
  `requests`, `errors`, `wait_seconds`이며 마지막 값은 소유 스레드의 future 회수 대기다.
  순차 실행에서는 이 값이 0이어도 실제 HTTP 시간이 0이라는 뜻은 아니다.

## 검증 및 재현

`tools/benchmark_boundary_prepare.py`는 기준 DB를 읽기 전용으로 열고 원본 SHA,
원본/API/버전 식별자, 각 페이지 입력 fingerprint를 대조한다. 새 출력 폴더에만 쓴다.
기본 모드는 기존 후보 문자열을 고정하여 입력 PNG, 전체 레이아웃·감사 판정·페이지
체크포인트를 비교한다. `--live`만 실제 인식을 호출하고 차이가 나면 exit 1로 보관한다.
이 검사는 원본 정답률 측정이 아니며 모델의 반복 실행 변동을 숨기지 않는다.

```powershell
python -m unittest discover -s tests -p test_boundary_prefetch.py -v
python tools/benchmark_boundary_prepare.py --source tmp/cpu_workers/production32/source.pdf --baseline tmp/performance-max/vram-controlled-a2-full-output --out tmp/NEW-boundary --overlap --repeats 2
```

실제 속도 비교는 OCR/회귀 테스트가 실행되지 않는 상태에서 위 명령에 `--live`를
추가한다. 순차 → 겹치기 → 겹치기 → 순차 순서로 실행한다. 서버를 재시작하지 않는다.

초기 CPU 분석에서 32페이지/347개 경계 후보/26개 OCR 입력의 준비는 중앙값 2.996초였다.
프로파일은 래스터 생성 약 2.227초, 경계 탐지 약 0.566초를 가리켰다(중첩 누적 시간).
전체 경계 단계 약 25초에 비해 작으므로 별도 CPU 프로세스 풀 대신 HTTP 겹치기를 선택했다.
고정 응답 교차 실행은 순차 2.600초/겹치기 2.604초로 비슷하며 CPU 알고리즘 자체가
빨라졌다는 주장이 아니다. 네 실행 모두 26개 PNG와 전체 결과/체크포인트가 일치했다.

운영 CLI/경계 모듈의 변경 전 스냅샷은 `tmp/performance-max/boundary-prefetch-rollback/`에
보관했다. 복구는 먼저 `--no-prefetch`를 사용한다. 스냅샷을 덮어쓰면 그 이후 변경까지
사라질 수 있으므로 파일 복구는 현재 변경과 비교한 뒤 선택적으로 적용한다.
운영 원본·캐시·기존 결과는 삭제하거나 덮어쓰지 않았다.

## 실제 비교의 해석

첫 실행(`boundary-prefetch-live`)은 전체 회귀 테스트와 CPU를 공유했으므로 속도 근거에서
제외한다. 네 실행 모두 결과와 체크포인트는 기준과 일치했다. 이어 모든 회귀가 끝난 뒤
`boundary-prefetch-isolated`에서 동일한 서버로 단독 비교했다.

| 실행 | 방식 | 경계 단계 시간 |
|---|---|---:|
| 1 | 순차 | 23.950초 |
| 2 | 겹치기 | 23.399초 |
| 3 | 겹치기 | 24.789초 |
| 4 | 순차 | 25.744초 |

중앙값 24.847 → 24.094초(약 3.0%). 차이가 작고 두 방식의 실행 시간이 겹치므로
확정적인 속도 향상으로 해석하지 않는다. 요청 PNG 26개와 전체 결과/체크포인트는 네 번
모두 기준과 일치했다. 전체 PDF 처리 시간이나 GPU 100% 유지에 대한 수치는 아니다.
추가 측정은 `boundary-prefetch-timed`에 저장하고 각 요청 HTTP 시간을 따로 기록한다.
`outside_http_seconds`는 경계 단계 전체 시간에서 겹치지 않는 HTTP 호출 시간 합을 뺀 값이다.
클라이언트의 요청 전후 준비·저장 등이며 **GPU가 실제 쉰 시간**을 뜻하지 않는다.

HTTP 시간을 분리한 추가 단독 비교:

| 실행 | 방식 | 경계 단계 | HTTP 바깥 시간 |
|---|---|---:|---:|
| 1 | 순차 | 25.603초 | 2.964초 |
| 2 | 겹치기 | 24.367초 | 1.163초 |
| 3 | 겹치기 | 24.526초 | 1.177초 |
| 4 | 순차 | 25.696초 | 2.967초 |

- 단계 중앙값 25.650 → 24.447초(약 4.7% 단축).
- HTTP 바깥 중앙값 2.965 → 1.170초(약 60.5% 감소). 기존 요청 입력·개수·동시성은 같다.
  추가 CPU 풀 없이 다음 입력 준비를 HTTP와 겹친 효과이며 서버 HTTP 자체의 속도 향상은 아니다.
- 추가 네 실행도 입력 PNG·전체 레이아웃·후보 문자열·채택/거부·체크포인트가 기준과 동일하다.
  누적 실제 12회 중 속도용 단독 실행은 8회이며 최초 경쟁 부하 4회는 제외한다.
- GPU 신선도 2초 이내의 1초 표본 평균은 순서대로 45.73/45.63/48.17/45.96%다.
  Windows 5초 계측에는 Chrome의 같은 3D 엔진 28~29% 표본도 남아 있다. 따라서
  전체 GPU 사용률을 OCR 사용률로 해석하거나 모든 외부 부하가 없었다고 주장하지 않는다.
  네 구간 모두 유효 표본에서 10% 이하가 없었지만 순차에서도 같고 외부 GPU 부하가 있으므로
  이번 변경이 저사용률 구간을 제거했다는 증거가 아니다. 1초 미만 공백도 포착하지 못한다.
- 현재 서버 VLM 예약은 기존 0.8이며 이 실험에서는 서버/WSL 재시작이나 HPS 설치가 없었다.

측정 원문은 `tmp/performance-max/boundary-prefetch-{isolated,timed}/`의 비교·각 응답과
동명의 `-profile/` 로그/자원 표본이다. 출력은 모두 실험용 새 디렉터리에만 생성했다.

최종 전체 오프라인 회귀는 **239개 통과(168.510초)**, 구조 검사는 Python 파일 88개/
구현 모듈 24개 통과다. 새 경계 동시성·오류·재개 회귀 9개와 CLI 기본/순차 옵션 검사 1개를
포함한다. 회전/cropbox/주석 PDF의 렌더링 소유권, PNG 바이트, Unicode 채택/거부와
페이지 체크포인트 순서도 대조했다. `git diff --check` 공백 오류는 없다.

동일함을 확인한 경계 레이아웃을 기준으로 downstream overlay도 새 캐시에서 재생했다.
`benchmark_cpu_startup.py --offline-replay`가 원시 PNG 응답 키 771개만 재사용하고
탐지/입력 PNG를 다시 생성했으며 새 HTTP는 0회다. 32페이지 전부 기존 PDF와 픽셀,
글자/글자 좌표, 페이지 판정과 line decisions가 일치했다. 기존 미배정 상자 48개는
그대로이며 이번 변경으로 해당 품질 경고를 해결했다고 보지 않는다.
검증 자료는 `tmp/performance-max/boundary-prefetch-pdf-check/comparison.json`이다.
이 실행은 회귀와 일부 겹쳤으며 속도 비교에는 사용하지 않는다.
