# VRAM 예약 교차 실험 — 기본 반영 보류

> 특정 입력과 당시 환경의 실험 기록이다. 원본, 교정 JSON, `tmp/` 및 문서별 fixture는
> 공개 저장소에 포함하지 않는 로컬 자료다.

## 결론과 현재 상태

`gpu_memory_utilization: 0.6`은 일부 속도·메모리 측정에서 유리했지만, 원문 대조에서
후보 응답의 추가 오독을 확인해 **기본 반영을 보류하고 기존 0.8로 복구했다**.
설정 파일과 실제 vLLM metrics의 0.8, KV 블록 23,836개, healthy 및 실행/대기 요청 0을 확인했다.
원본 PDF·기존 OCR 캐시·모델·API/줄 OCR 설정은 바꾸지 않았다. HPS를 재도입하지 않았다.

이 옵션은 GPU 연산 사용률 목표가 아니라 인스턴스의 모델 실행기 메모리 예산이다.
[설치된 vLLM 0.10.2 공식 설명](https://docs.vllm.ai/en/v0.10.2/configuration/engine_args.html#gpu-memory-utilization).
메모리 예약을 줄이는 것은 해상도/양자화 변경이 아니지만, 그것만으로 새 출력의 동일성이나
정답률이 증명되는 것은 아니다. 이번에는 속도보다 사용자의 정확도 유지 조건을 우선했다.

## 비교 조건

- 순서: A1(기존 0.8) → B1(0.6 재시작) → A2(0.8 재시작) → B2(0.6 재시작).
  B2 검사가 끝난 뒤 0.8로 복구했다. 모든 재시작은 OCR 프로세스/요청 종료를 확인한 뒤
  VLM 컨테이너 하나에만 수행했다. API·줄 OCR 및 별도 컨테이너는 재시작하지 않았다.
- 같은 10페이지 PDF bytes를 각 조건에서 3회 순차 인식했다. 클라이언트/API 옵션은 같다.
  요청 SHA-256: `310041e180dbbedefcb5b6a30ad4341194ca3ec851c00602e607a8ba81963828`.
- B1/A2/B2에서는 3회 반복 직후 새 폴더의 32페이지 전체 OCR도 수행했다.
  완전히 새 결과/줄 캐시를 사용했고 기존 운영 DB는 수정하지 않았다.
- 모델, BF16, 최대 문맥 16,384, 배치 토큰 131,072, 해상도·입력 크기·검출 임계값은 유지했다.
  실제 startup log에서 0.8은 KV 381,376 tokens, 0.6은 196,208 tokens를 확인했다.
  예산 외 GPU 메모리까지 모두 통제하는 OS 강제 상한은 아니다.
- A1은 장시간 실행된 서버, 나머지는 재시작 직후다. 첫 요청 제외 시간도 표시하지만
  동일한 워밍업/메모리/OS 캐시 상태를 완전히 보장하는 무작위 대규모 실험은 아니다.

## 성능과 자원 관측

| 조건 | 10페이지 3회 시간 | 첫 회 제외 중앙값 | GPU 메모리 표본 중앙값 |
|---|---|---:|---:|
| A1 / 0.8 | 18.696 / 9.613 / 10.058초 | 9.835초 | 15,333 MiB |
| B1 / 0.6 | 22.113 / 8.902 / 8.027초 | 8.465초 | 14,045 MiB |
| A2 / 0.8 | 28.429 / 12.492 / 9.471초 | 10.981초 | 15,504 MiB |
| B2 / 0.6 | 22.156 / 9.300 / 8.231초 | 8.766초 | 15,448 MiB |

B1의 GPU 메모리는 약 1.3 GiB 낮았지만 B2는 그러지 않았다. startup log상 B2도 실제
0.6이므로 조건 이름을 잘못 붙인 것은 아니다. NVIDIA 수치는 GPU 전체/다른 앱/예약·주재 상태를
포함하며, **항상 1.3 GiB를 절약한다는 결론은 내리지 않는다**. Windows 엔진별 값은 합산하지 않는다.
0.6 반복의 신선한 KV 사용률 최고는 B1 약 38.8%, B2 약 20.9%였다. 관측한 선점 누계는 0이었다.

전체 32페이지 시간:

| 조건 | CLI 전체 시간 | 검증 |
|---|---:|---|
| 직전 장시간 0.8 상태 | 180.568초 | 완료, 기존 경고 |
| B1 / 0.6 | 99.544초 | 완료, 기존 경고 |
| A2 / 재시작한 0.8 | 103.906초 | 완료, 기존 경고 |
| B2 / 0.6 | 99.014초 | 완료, 기존 경고 |

0.8을 재시작해도 103.9초로 줄었으므로 180.6 → 99초를 모두 예약값 변경의 개선으로
주장하지 않는다. 유사 순서의 A2와 B1/B2에서는 약 4~5% 차이이며 조건별 표본 수가 작다.
같은 CPU 상한에서도 메모리 입장에 따라 실제 작업자 수가 달랐다. B1/B2의 보완은 4개,
overlay는 9/11개, 검증은 8개였다. GPU 사용률 100% 유지나 저사용 구간 제거는 달성하지 않았다.

## 정확도 게이트: 통과하지 못함

12회 모두 블록 좌표/식별자/순서는 같았지만 문자열은 변했다. 각 3회 반복의 엄격한
동일성 검사 종료 코드는 모두 1이었다. 이것만으로 어느 설정이 더 정확한지 알 수 없어
변한 문장을 원본 이미지로 직접 확인했다.

진단 원본 PDF의 6페이지, 블록 16에는 다음 문장이 있다.

> (3) 덱을 이용하면 깊이우선탐색과 너비우선탐색을 모두 구현할 수 있다.

PDF crop `[550,2940,2500,3150]`을 렌더링한
`tmp/performance-max/vram-controlled-glyph-source.png`에서 **덱**을 확인했다.

| 설정 | 이 문장 대조 결과 |
|---|---|
| 0.8 / A1·A2 | 6/6 일치 |
| 0.6 / B1·B2 | 4/6 일치; B1의 2회차와 B2의 1회차에서 `덱` → `텍` |

표본이 작고 기존 모델도 변동하므로 예약값이 오류의 원인이라고 확정하지 않는다.
그러나 정확도 유지를 입증하지 못한 후보를 성능만으로 기본 적용하지 않는다.
이 한 문장 검사는 전체 책 정답률이 아니며, 다른 목차/숫자/코드 오독이 없다는 뜻도 아니다.

최종 PDF 화면 픽셀은 32페이지 모두 같았지만 A2와 B1은 글자/좌표 1·6·10·32페이지,
A2와 B2는 1·4·6·10·15·31·32페이지가 달랐다. 페이지 1 finding과 line decision도 달라
전체 엄격 비교는 실패로 보관했다. 보완 전 문단 문자열부터 차이가 있고 문단 박스 및
공통 줄 이미지 응답 771개는 같았다. 화면 픽셀 검증 통과를 인식 정확도 통과로 바꾸지 않는다.

## 남긴 개선과 재현

`tools/compare_document_trials.py`는 저장된 요청 bytes/옵션을 검증하고 시간과 문자 변동,
신선한 GPU/메모리 지표를 분리한다. 선택적 `--checks`는 원본 요청 해시·페이지·블록 ID·박스에
묶인 직접 대조 항목을 검사한다. 미일치나 누락을 성공으로 처리하지 않고 exit 1을 반환한다.
원문 대조 항목은 `docs/fixtures/vram_deque_check.json`이며 자동 OCR/캐시에 정답을 덮어쓰지 않는다.

```powershell
python tools/compare_document_trials.py tmp/performance-max/vram-controlled-a1 tmp/performance-max/vram-controlled-b1 tmp/performance-max/vram-controlled-a2 tmp/performance-max/vram-controlled-b2 --out tmp/NEW-vram-check.json --checks docs/fixtures/vram_deque_check.json
python -m unittest discover -s tests -p test_document_trials.py -v
```

첫 명령은 위 두 오독 때문에 exit 1이 정상적인 진단 결과다. 새 오프라인 회귀 6개와
Python 파일 86개/구현 모듈 24개 구조 검사가 통과했다. 직전 전체 회귀는 223개였으며,
이번에는 운영 Python 알고리즘을 변경하지 않았다. 기준 설정 파일은
`tmp/performance-max/vram-controlled-rollback/vllm_config.yml`에 보관했다.
복구된 설정값은 0.8이고 편집 과정에서 파일 끝 개행만 추가됐다.

원시 자료는 `tmp/performance-max/vram-controlled-*`의 반복 응답, 전체 출력, profile,
`*-comparison.json` 및 `*-input-variation.json`이다. 다음은 장기 실행/재시작 차이의
메모리 원인과, 입력/출력을 정확히 보존할 수 있는 경계 보완의 CPU 준비 병렬화다.
