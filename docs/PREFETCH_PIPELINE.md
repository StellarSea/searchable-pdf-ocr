# 한 문단 선행 준비 파이프라인

자동 모드에서 현재 문단의 줄 OCR을 요청한 뒤 응답을 기다리는 동안, 다음 문단
하나의 줄 좌표와 PNG를 준비한다. `--no-prefetch`로 기존 순차 실행을 선택할 수 있다.
이 옵션은 스케줄링만 바꾸므로 기존 완료 판정이나 이미지/검토 캐시 키는 바꾸지 않는다.

## 소유권과 제한

- PDF, Page, DisplayList, Font, SQLite, 보고서와 삽입 순서는 모두 기존 메인 스레드가 소유한다.
- 추가 작업자는 하나이며 `recognize_lines`에 PNG bytes와 언어만 전달한다.
  이 작업자는 HTTP 직렬화/전송/응답 확인만 한다. GPU 요청도 한 번에 하나다.
- PDF 객체를 여러 스레드에서 쓰지 않으며, PDF 전체를 다른 프로세스에서 다시 여는 비용도 없다.
- 다음 문단 하나만 준비한다. 페이지를 넘어가거나 문서 전체를 미리 렌더링하지 않는다.
- 추가로 보관하는 PNG 버퍼는 최대 64 MiB다. 예상 작업 크기가 남은 예산을 넘는
  crop은 선행 준비하지 않고 원래 위치에서 같은 해상도로 렌더링한다.
- 이 제한은 **추가 PNG 버퍼** 기준이며 전체 프로세스 RSS 제한은 아니다.
  MuPDF의 원본 이미지 디코딩, 현재 요청, 레이아웃 배열과 폰트 메모리는 별도로 존재한다.
- 이미 응답 캐시가 있는 줄은 선행 렌더링하지 않는다. 캐시가 모두 준비된 실행은
  HTTP 작업자 스레드를 실제로 시작하지 않는다.
- HTML/표/수식은 선행 준비 대상에서 제외하며 원래 순서로 처리한다.

## 정확도와 실패 처리

원래 줄 탐지/표 배치/문자 분할 경로를 `_block_layout`으로 묶어 선행 준비에서도 같은
함수를 호출한다. 원본 표시 목록은 투명 텍스트를 삽입하기 전에 캡처한 `PageRaster`다.
미리 만든 PNG를 소비할 때도 응답 캐시를 다시 조회하고, 기존 방식으로 PNG 해시와
블록 검토 키를 계산한다. 다음 문단의 글자를 먼저 삽입하거나 결정 기록을 먼저 쓰지 않는다.

선행 준비에서 예외가 나면 해당 버퍼를 채택하지 않고 정상 차례에 다시 처리한다.
빈 탐지 결과도 일시적인 렌더 실패일 수 있으므로 선행 배치 결과로 보관하지 않는다.
OCR 요청 실패는 기존 복구/재시도/중단 규칙을 따른다. 종료 시 HTTP 작업자가 끝난 뒤
문서를 닫으며, 검증 전 감사 기록을 게시하는 동작은 없다.

인식 모델, 입력 폭, GPU 작업자 수, 렌더 배율, 탐지 임계값, 문자/숫자 보존 규칙과
최종 검증은 바뀌지 않았다. 이미 잘못 인식된 글자를 새로 교정하는 기능은 아니다.

## 측정값

보고서의 `prefetch_stats`는 선행 준비 문단 수(`blocks`), PNG 수(`crops`), 최대 버퍼
바이트(`peak_buffer_bytes`), 선택적 준비 실패 수(`errors`), 준비 시간의 합
(`prepare_seconds`), 준비 후 HTTP 결과를 추가로 기다린 시간(`wait_seconds`)이다.
준비 시간 전체가 GPU와 겹쳤다는 뜻은 아니며 이 값들을 더해 전체 처리 시간을 계산하면 안 된다.

`tools/benchmark_prefetch.py`는 새 진단 폴더에서 캐시가 없는 순차/선행 준비 실행을
번갈아 비교하고, 매 실행마다 인식 문자열·배치 결정·캐시 키·글자 좌표·PDF 픽셀을
검사한다. 같은 캐시의 재실행에서는 OCR 호출이 없다는 것도 확인한다.
운영 원본/캐시는 읽기만 하고 서버는 시작하거나 재시작하지 않는다.

실제 측정 자료는 `tmp/prefetch/live/comparison.json`, 목차 6/7페이지와 본문
166페이지의 변경 전 비교는 `tmp/prefetch/layout/comparison.json`에 보관한다.
속도 비교는 문단 OCR 이후 overlay 구간이며 책 전체 최초 OCR 시간은 아니다.

## 2026-09-13 실측과 검증

문단이 많은 38/66/147/166/188페이지를 선택했다. 53개 문단의 158줄을 실제 HTTP/GPU로
인식했고, PDF에 삽입한 전체 줄 수는 199개다. 각 실행은 별도 빈 캐시를 사용하며
실행 순서를 순차/선행, 선행/순차, 순차/선행으로 바꾸었다.

| 실행 | 순차 overlay | 선행 준비 overlay |
|---|---:|---:|
| 1 | 32.540초 | 27.322초 |
| 2 | 30.447초 | 30.439초 |
| 3 | 27.722초 | 22.978초 |
| 중앙값 | 30.447초 | 27.322초 |

중앙값 기준 약 10.3% 단축이다. 실행별 변동이 있고 한 쌍은 사실상 차이가 없었으므로,
모든 문서에서 일정한 개선률을 보장하지 않는다. 특히 페이지당 문단이 하나뿐이거나
캐시가 이미 채워졌다면 겹쳐 실행할 작업이 적다. 캐시 재실행은 양쪽 모두 약
1.2~1.5초였고 OCR 호출은 없었다. 초기 문단 OCR 및 최종 검증 시간은 이 측정에서 제외했다.

선행 실행마다 50개 문단의 배치를 준비하고 PNG 112개를 미리 만들었다. 추가 PNG
버퍼의 실제 최대값은 960,479 bytes(약 0.92 MiB), 준비 오류는 0개였다.

모든 실제 비교 실행의 인식 후보, 선택 문자열, 줄 순서, PNG/검토 키, 품질 보고서,
글자 좌표와 PDF 픽셀이 동일했다. 처리 시간/캐시 적중률 등 성능 통계만 비교에서 제외한다.
별도 6/7/166페이지 비교도 변경 전과 동일했고, PDF 스킬의 시각 검증 절차로 목차와
본문 PNG를 확인했다. 이 결과는 동작 보존 확인이며 전체 책의 모든 글자가 정답이라는 뜻은 아니다.

서버 재시작이나 모델 변경은 필요 없으며 다음 자동 OCR 실행부터 적용된다.
실행 중인 작업이나 기존 최종 PDF/운영 캐시를 강제로 재처리하지 않았다.

전체 오프라인 회귀 테스트 101개가 통과했다(51.291초). 추가 테스트는 실행 겹침,
단일 PDF/SQLite 소유권, 버퍼 예산, 캐시 재사용, 선행 렌더 실패/빈 탐지 재시도,
HTTP 실패 시 작업자 종료와 기존 감사 기록 보존을 확인한다.
Python 파일 40개 문법 검사, 구현 모듈 14개 순환 의존성 검사와 `git diff --check`도 통과했다.
